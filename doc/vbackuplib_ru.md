# VBACKUP -- сохранить файлы в saveset, восстановить, сравнить

VBACKUP хранит копии файлов в saveset-е. Saveset -- это один файл или
несколько файлов-томов. В нём лежат сами файлы, их владельцы, права,
времена, расширенные атрибуты и ACL. Ещё в нём есть контрольные суммы,
поэтому повреждение всегда обнаруживается, и запасные блоки, поэтому
небольшое повреждение исправляется.

VBACKUP работает как команда BACKUP в OpenVMS. Вы говорите, что читать
и куда писать:

```
VBACKUP входная-спецификация[,...] выходная-спецификация [/квалификаторы]
```

Что будет сделано, зависит от двух сторон:

```
файлы    ->  saveset       сохранение       vbackup /home/rrl rrl.bck
saveset  ->  каталог       восстановление   vbackup rrl.bck /tmp/back
saveset  /LIST             листинг          vbackup rrl.bck /LIST
saveset  /COMPARE          сравнение        vbackup rrl.bck /COMPARE
saveset  /EXTRACT=имя      один файл        vbackup rrl.bck /EXTRACT=rrl/a.txt
файлы    ->  каталог       копирование      vbackup /home/rrl /mnt/copy
saveset  /RECORD           в журнал         vbackup rrl.bck /RECORD
/JOURNAL /LIST             журнал           vbackup /JOURNAL /LIST
```

Saveset на входе VBACKUP узнаёт по содержимому, а не по имени. При
сохранении он понимает, что выход -- saveset, если имя кончается на
.bck, если дан /SAVE_SET или если имя "-" (стандартный вывод).

Шаблоны берите в кавычки -- VBACKUP раскрывает их сам:

```
$ vbackup '/home/rrl/.../*.c' sources.bck
```

Квалификатор можно сокращать, пока сокращение однозначно: /VER вместо
/VERIFY. Можно писать и по-юниксовому: --VERIFY. Слово, начинающееся с
косой черты, считается квалификатором, только если оно называет
квалификатор, поэтому /etc и /home -- это имена файлов. Одиночный
\`--\` заканчивает квалификаторы.

Код завершения: 0 -- всё хорошо, 1 -- были предупреждения (например,
файл менялся во время сохранения), 2 -- что-то не сделано (например,
файл не удалось прочитать).

## Параметры

### входная-спецификация

При сохранении: файлы и каталоги, через запятую. Каталог сохраняется
со всем содержимым. См. тему ШАБЛОНЫ.

При восстановлении, листинге, сравнении и извлечении: saveset. Дайте
имя первого тома, остальные тома VBACKUP найдёт сам.
Saveset, записанный OpenVMS BACKUP, тоже читается: см. тему OPENVMS.

Saveset может прийти по каналу: "-" -- стандартный ввод.

```
ssh host 'vbackup /home -' | vbackup - /restore
vbackup /home - | ssh host 'vbackup - /backup/home.bck'
```

Восстановление, /LIST, /COMPARE, /EXTRACT и vbkx читают его по мере
поступления, один раз, только вперёд; каталог в его конце тут не
помогает, поэтому файл для /EXTRACT ищется чтением. Плохие блоки
чинятся как из файла. Saveset, записанный в "-", несёт свои тома
(/VOLUME_SIZE) подряд; канал, оборвавшийся до конца saveset-а, даёт
NOTRAILER.

Saveset на другом узле, как писал DECnet, -- узел::файл:

```
vbackup /home host::/backup/home.bck /VOLUME_SIZE=4G /VERIFY
vbackup host::/backup/home.bck /restore
vbackup host::/backup/home.bck /LIST
```

VBACKUP работает и там, через ssh (VBACKUP_RSH называет другую
команду), а saveset идёт по каналу: при сохранении он раскладывается
там по файлам томов, каждый блок проверяется по прибытии; /VERIFY
читает его оттуда обратно и сравнивает с диском здесь. Сообщения той
стороны приходят сюда; её код завершения становится здешним
(REMOTEERR). На другом узле нужен VBACKUP X01-11 или новее в PATH ssh,
и он должен пускать этот узел по ключам. /DELETE и /LIST с saveset-ом,
создаваемым на другом узле, не принимаются.

При восстановлении можно дать несколько saveset-ов через запятую - они
восстанавливаются по очереди. С /INCREMENTAL сначала полный saveset,
затем инкрементальные в том порядке, в каком они делались.

При копировании: файлы и каталоги, как при сохранении.

### выходная-спецификация

При сохранении: создаваемый saveset. Если он уже есть, VBACKUP
остановится; /REPLACE -- перезаписать.

При восстановлении: каталог, куда восстанавливать. Создаётся при
необходимости.

При сравнении: каталог, с которым сравнивать. Без него файлы
сравниваются с теми местами, откуда были сохранены.

При извлечении: файл, куда писать. Без него или с "-" -- стандартный
вывод.

При копировании: каталог, куда копировать. Выход, который не saveset
(нет .bck или .sav, нет /SAVE_SET), означает копирование, как в BACKUP.
Файлы получают всё то же, что вернуло бы восстановление.

Берутся только эти два параметра. Третье слово -- ошибка
(%VBACKUP-E-MAXPARM): чаще всего это квалификатор без косой черты --
".log" вместо "/LOG".

Квалификаторы можно приклеивать к параметру, как в DCL: "x.sav/sav/log"
-- это "x.sav /SAVE_SET /LOG". VBACKUP об этом сообщает
(%VBACKUP-I-GLUED), чтобы опечатка в имени файла не была молча принята
за квалификатор. Слово, которое является именем существующего файла,
не разрезается; квалификатор со значением, содержащим косую черту
(/JOURNAL=/var/...), пишется отдельно.

## /SAVE_SET -- выход это saveset

Говорит, что выходная спецификация -- saveset, как бы она ни
называлась. Не нужен, если имя кончается на .bck или .sav (так
называются saveset-ы в OpenVMS).

## /BLOCK_SIZE -- размер блока

```
/BLOCK_SIZE=n
```

Saveset состоит из блоков по n байт: от 8192 до 1048576, кратно 512.
По умолчанию 65536. Большие блоки чуть быстрее, маленькие -- меньше
теряется при порче одного блока.

## /GROUP_SIZE -- запасные блоки для починки

```
/GROUP_SIZE=n
```

После каждых n блоков данных VBACKUP пишет один XOR-блок. Если в
группе испортился один блок, при чтении он восстанавливается из
остальных: вы увидите %VBACKUP-I-BLKFIXED, и ничего не потеряно.

По умолчанию 10: saveset больше на 10%. n от 0 до 100; /GROUP_SIZE=0 --
XOR-блоков нет, чинить нечем.

## /PARITY -- починка нескольких плохих блоков группы

```
/PARITY=m
```

Каждая группа получает m блоков чётности вместо одного XOR-блока: любые
m плохих блоков группы -- в том числе подряд, данные или чётность --
восстанавливаются при чтении saveset-а (Reed-Solomon). /PARITY=1 -- по
умолчанию, один XOR-блок. m от 1 до 8; нужны группы, не
/GROUP_SIZE=0.

```
$ vbackup /home /mnt/usb/home.bck /PARITY=2
$ vbackup /home /mnt/tape/home.bck /GROUP_SIZE=20 /PARITY=4
```

Saveset растёт на m/n: /GROUP_SIZE=10 /PARITY=2 делает его больше на
20%, /GROUP_SIZE=20 /PARITY=4 -- тоже, но второй переживает четыре
плохих блока подряд вместо двух. Это для носителей, которые портятся
пачками: старые диски, флешки, оптические диски, ленты.

Saveset с /PARITY=2 и больше -- формата версии 2. VBACKUP и vbkx до
X01-14 его не читают: говорят, что это не saveset. VBACKUP X01-14
читает оба. Зашифрованные saveset-ы, как всегда, чинятся без пароля.

Чётность считается векторными инструкциями процессора (AVX2 или SSSE3,
NEON на ARM), где они есть, -- примерно в десять раз быстрее, чем без
них; VBACKUP_NOSIMD=1 выключает их для поиска неисправностей.

## /VOLUME_SIZE -- нарезать saveset на тома

```
/VOLUME_SIZE=размер
```

Режет saveset на файлы такого размера. Нужно для диска с пределом
4 ГБ на файл (FAT32), для заливки в облако, для носителей
фиксированного размера. Размер может кончаться на K, M, G или T:

```
$ vbackup /home home.bck /VOLUME_SIZE=4G
```

Тома называются home.bck, home.bck.002, home.bck.003 и так далее.
Держите их вместе, в одном каталоге. Если том потерялся, файлы из
остальных томов всё равно восстанавливаются.

## /COMMENT -- заметка в saveset-е

```
/COMMENT="текст"
```

Сохраняет текст в saveset-е; /LIST его показывает.

## /ORIGINAL -- восстановить файлы туда, откуда они взяты

```
vbackup /mnt/usb/home.bck /ORIGINAL
vbackup /mnt/usb/home.bck /ORIGINAL /REPLACE     поверх существующих файлов
```

Выходной каталог не указывается: каждый файл возвращается в тот каталог,
откуда был сохранён (saveset хранит его абсолютным именем с X01-02).
Прежде чем писать, VBACKUP говорит, куда пойдут файлы. Существующие
файлы не трогаются без /REPLACE.

Saveset, сделанный до X01-02, не знает, откуда его файлы: укажите
выходной каталог (ORIGNOBASE). Saveset из нескольких входов кладёт
каждый файл под свой; /INCREMENTAL -- только для saveset-а с одним
входом.

Осторожно с чужими saveset-ами: /ORIGINAL пишет туда, куда говорит
saveset.

## /DELETE -- удалить файлы после сохранения

```
vbackup /home/ivan/old /mnt/usb/old.bck /VERIFY /DELETE
```

Сохраняет файлы, перечитывает saveset и сравнивает его с диском
(/VERIFY обязателен) и только потом удаляет файлы с диска. Файл
удаляется, только если сравнение не нашло никаких различий и файл не
менялся после сохранения (тот же inode, размер, время изменения данных и
метаданных); иначе он остаётся, и SRCKEPT говорит почему. Каталоги
остаются. /CONFIRM спрашивает про каждый файл, /LOG называет каждый
удалённый.

/DELETE не сочетается с /PHYSICAL, /IMAGE, /SINCE и /BEFORE и ничего не
удаляет, если saveset идёт на стандартный вывод (его нельзя проверить).

## /PHYSICAL -- устройство целиком, поблочно

```
vbackup /dev/sdb1 /mnt/usb/sdb1.bck /PHYSICAL          сохранить устройство
vbackup /mnt/usb/sdb1.bck /dev/sdc1 /PHYSICAL /REPLACE восстановить на устройство
vbackup /mnt/usb/sdb1.bck /tmp/sdb1.img /PHYSICAL      восстановить в файл-образ
vbackup /mnt/usb/sdb1.bck /tmp/dir                     то же: dir/sdb1 -- образ
```

Копирует каждый блок устройства -- раздела или целого диска -- или
файла-образа: любая файловая система, зашифрованные тома, загрузочные
области. Блоки из нулей места в saveset-е не занимают. Работает и с
/DATA_FORMAT=COMPRESSED. Запускать от root.

Чем рискуем и что VBACKUP с этим делает:

- Устройство, на которое пишут во время копирования, даёт битую копию,
  и это не видно, пока она не понадобится. Устройство, смонтированное на
  запись (или с таким разделом), VBACKUP не берёт. Размонтируйте его,
  смонтируйте только на чтение или копируйте снимок (LVM, btrfs).
- Занятое устройство -- физический том LVM, член RAID, контейнер
  dm-crypt, swap -- тоже не берётся.
- Восстановление переписывает выходное устройство целиком. VBACKUP
  делает это только с /REPLACE, никогда на смонтированное или занятое
  устройство и никогда на меньшее, чем сохранённое. За терминалом надо
  набрать YES. Скрипт даёт /REPLACE, и его не спрашивают.
- На большее устройство копия ложится в начало; файловая система
  остаётся прежнего размера (увеличьте её resize2fs, xfs_growfs ...).
- У копии те же метки и UUID, что у оригинала. Никогда не монтируйте их
  одновременно: xfs откажется, btrfs может испортить оба.
- Потерянный блок saveset-а -- потерянный кусок устройства:
  восстановление скажет FILDAMAGED. Держите /GROUP_SIZE небольшим и
  две копии важного.

/PHYSICAL берёт один вход и не сочетается с /SELECT, /EXCLUDE, /SINCE,
/BEFORE, /BY_OWNER, /RECORD и /INCREMENTAL: устройство -- не дерево
файлов.

## /IMAGE -- файловая система целиком, пересоздаётся при восстановлении

```
vbackup /mnt/data /mnt/usb/data.bck /IMAGE             сохранить том
vbackup /dev/sdb1 /mnt/usb/data.bck /IMAGE             то же, по устройству
vbackup /mnt/usb/data.bck /dev/sdc1 /IMAGE /REPLACE    создать его заново на устройстве
vbackup /mnt/usb/data.bck /tmp/dir                     только файлы, в каталог
```

Сохраняет все файлы одной файловой системы -- целиком, без других
файловых систем, смонтированных внутри неё, -- и то, что делает её этим
томом: тип, метку, UUID, владельца и права корня. На входе -- точка
монтирования или устройство, если оно смонтировано (хватит и только на
чтение). Запускать от root.

Восстановление с /IMAGE создаёт на выходном устройстве новую файловую
систему того же типа, с той же меткой и UUID (запускается mkfs.ext4,
mkfs.xfs, mkfs.btrfs или mkfs.vfat -- программа должна быть
установлена), восстанавливает в неё файлы и размонтирует. Устройство
может быть меньше или больше сохранённого -- лишь бы файлы поместились.

Защита та же, что у /PHYSICAL: /REPLACE, никогда на смонтированное или
занятое устройство, YES за терминалом; у копии UUID оригинала -- никогда
не монтируйте их одновременно.

Чем /IMAGE не является: копией загрузочных секторов и таблицы разделов
(для этого сохраните весь диск с /PHYSICAL) и номеров inode. Том, на
который пишут во время сохранения, согласован пофайлово, но не между
файлами: если это важно, сохраняйте снимок. Другие типы файловых систем
(minix, ntfs ...): /PHYSICAL.

/IMAGE сочетается с /RECORD, /SINCE, /VERIFY и /DATA_FORMAT; не
сочетается с /SELECT, /EXCLUDE, /BY_OWNER, /INCREMENTAL, /PHYSICAL, а при
восстановлении -- с /CONFIRM.

## /DATA_FORMAT -- сжимать данные

```
/DATA_FORMAT=COMPRESSED
/DATA_FORMAT=UNCOMPRESSED     (по умолчанию)
```

COMPRESSED делает saveset меньше: тексты, программы и документы часто
сжимаются вдвое и сильнее. Уже сжатые файлы (фото, видео, .gz, .zip)
остаются как есть: VBACKUP пробует первые 64 КБ каждого куска и, если
они не сжимаются, пишет кусок без сжатия -- это почти не стоит времени.
Контрольные суммы и починка плохих блоков работают как обычно.

Сжатие идёт на всех ядрах машины (не больше 8); saveset тот же, что и
на одном. VBACKUP_ZTHREADS=n в окружении задаёт число потоков, 1 --
без потоков.

Восстановлению, /LIST, /COMPARE, /EXTRACT и vbkx ничего указывать не
надо: сжатые данные они узнают сами.

Внимание: VBACKUP и vbkx версий до X01-04 сжатые данные читать не
умеют. Неверных файлов они не пишут: сжатые файлы они называют
повреждёнными (CRCERR, FILDAMAGED). Обновите их.

Пример: vbackup /home /mnt/usb/home.bck /DATA_FORMAT=COMPRESSED

## /TRANSFER -- saveset в saveset, блок за блоком

```
vbackup x.bck y.bck             копия, том за томом
vbackup x.bck -                 тома подряд на вывод
vbackup - y.bck                 поток в y.bck, y.bck.002, ...
```

Когда вход -- saveset и выход -- saveset, блоки копируются как есть --
никогда не записи: зашифрованному saveset-у пароль не нужен, а копия
побайтно совпадает с оригиналом. Каждый блок проверяется по дороге;
плохой копируется как есть и называется (BLKCOPIED) -- восстановление
починит его по группе. /TRANSFER требует этого, что бы ни значили
имена (узел::файл им пользуется, чтобы старый VBACKUP на другом узле
отказал, а не восстановил).

## /ENCRYPT -- зашифрованный saveset

```
vbackup /home/me me.bck /ENCRYPT
vbackup /home/me me.bck /ENCRYPT /KEY_FILE=/root/backup.key
```

Данные, имена файлов и всё остальное в saveset-е шифруется паролем
(парольной фразой); без неё ничего не прочитать. VBACKUP дважды
спрашивает пароль на терминале (при вводе ничего не видно) или берёт
его из файла ключа (/KEY_FILE). В командной строке пароль не задаётся
никогда: командная строка хранится в saveset-е, и её видят другие
пользователи через ps.

Восстановление, /LIST, /COMPARE, /EXTRACT и vbkx сами видят, что
saveset зашифрован, и спрашивают пароль (или берут /KEY_FILE).
/ENCRYPT даётся только при сохранении.

Повреждённый зашифрованный saveset чинится как любой другой: проверке
и починке пароль не нужен. Блок, который кто-то изменил нарочно (и
подправил контрольную сумму), распознаётся по метке аутентификации,
сообщается (%VBACKUP-W-BLKFORGED) и чинится по своей группе, как
плохой блок.

Пароль -- это и есть ключ. Храните его надёжно: никто, включая автора
VBACKUP, не откроет saveset с потерянным паролем. Берите длинный --
пять и больше случайных слов. Журнал (/RECORD) не шифруется: это файл
этой системы.

Шифрование идёт на нескольких ядрах: ключевой поток блока -- полосами,
блоки группы при чтении проверяются и расшифровываются параллельно.
VBACKUP_CTHREADS=n -- число потоков, 1 -- без них.

Как: ChaCha20 и HMAC-SHA256 на каждый блок, ключи из пароля через
PBKDF2-HMAC-SHA256 с 600000 итераций и случайной солью для каждого
saveset-а (format.md, 6.10). Библиотеки не используются: vbkx и
извлекатели для гиков читают его, ни в чём больше не нуждаясь.

Замечание: VBACKUP и vbkx до X01-06 зашифрованный saveset прочитать не
могут; они сообщают, что все блоки потеряны, и ничего не пишут.

## /KEY_FILE -- пароль из файла

```
/KEY_FILE=файл
```

Первая строка файла -- пароль (без конца строки). Файл должен быть
доступен на чтение только владельцу -- chmod 600 файл, -- иначе VBACKUP
его не примет (%VBACKUP-E-KEYFILE). Для сохранений из cron или
таймера и для файловых менеджеров.

Без /KEY_FILE берётся переменная окружения VBACKUP_KEY_FILE. Без обоих
VBACKUP спрашивает на терминале; если его нет (cron, канал), он
останавливается с %VBACKUP-E-NOKEY -- и никогда не ждёт.
VBACKUP_NOPROMPT=1 запрещает вопрос даже при наличии терминала (его
ставят плагины файловых менеджеров).

## /SELECT -- взять только некоторые файлы

```
/SELECT=(шаблон[,...])
```

Берёт только файлы, чьё хранимое имя подходит под шаблон. Работает
при сохранении, восстановлении, сравнении и листинге. В шаблоне *
означает любые символы (и / тоже), % и ? -- один символ:

```
$ vbackup home.bck /tmp/r '/SELECT=(*.c,*.h)'
```

Хранимое имя -- имя относительно базы saveset-а, например
rrl/src/a.c. /LIST показывает хранимые имена.

## /EXCLUDE -- исключить файлы

```
/EXCLUDE=(шаблон[,...])
```

Пропускает файлы, чьё хранимое имя подходит под шаблон. Подходящий
каталог пропускается целиком:

```
$ vbackup /home/rrl rrl.bck '/EXCLUDE=(*.o,*/.cache)'
```

## /SINCE -- только файлы, изменённые после момента

```
/SINCE=время
/SINCE=BACKUP
```

Сохраняет только файлы не старше указанного времени. Каталоги
сохраняются всегда. См. тему ВРЕМЯ.

/SINCE=BACKUP сохраняет только файлы, изменившиеся с тех пор, как их в
последний раз сохранили с /RECORD, -- это знает журнал. Файл, которого
журнал не знает, сохраняется. Без журнала сохраняется всё, как в первый
раз.

Любой /SINCE или /BEFORE делает saveset инкрементальным: файлы, которые
он не сохранил, всё равно перечислены в его каталоге как присутствующие.
См. тему ИНКРЕМЕНТЫ.

## /BEFORE -- только файлы старше момента

```
/BEFORE=время
```

Сохраняет только файлы старше указанного времени. См. тему ВРЕМЯ.

## /MODIFIED -- /SINCE и /BEFORE смотрят на время изменения

Так по умолчанию.

## /CREATED -- /SINCE и /BEFORE смотрят на время создания

Linux хранит время создания на ext4, xfs и btrfs. На файловой системе
без него файлы по этому времени не отбираются.

## /CHANGED -- /SINCE и /BEFORE смотрят на время смены атрибутов

Время смены (ctime) меняется и тогда, когда меняются права, владелец
или имя.

## /BY_OWNER -- только файлы одного пользователя

```
/BY_OWNER=пользователь
```

Сохраняет только файлы этого пользователя -- по имени или номеру.

## /CROSS_DEVICE -- заходить в другие файловые системы

```
/CROSS_DEVICE
/NOCROSS_DEVICE   (по умолчанию)
```

По умолчанию точка монтирования сохраняется как каталог, но то, что на
неё смонтировано, -- нет. Поэтому при сохранении / не попадут /proc,
/sys и подключённая флешка. /CROSS_DEVICE -- сохранить и их.

## /IGNORE -- сохранить то, что обычно пропускается

```
/IGNORE=NOBACKUP
```

Файлы и каталоги с флагом nodump (chattr +d) не сохраняются -- это
флаг NOBACKUP из OpenVMS. /IGNORE=NOBACKUP сохраняет и их.

## /XATTRS -- расширенные атрибуты и ACL

```
/XATTRS     (по умолчанию)
/NOXATTRS
```

Сохраняет и восстанавливает расширенные атрибуты, POSIX ACL,
capabilities файлов и метку SELinux. Часть из них восстановить может
только root.

## /VERIFY -- проверить saveset после записи

Записав saveset, VBACKUP читает его заново и сравнивает каждый файл с
диском. Различие сообщается как %VBACKUP-E-COMPARERR.

## /LOG -- сообщать о каждом файле

Сообщает о каждом сохранённом, восстановленном или сравнённом файле.

И без /LOG VBACKUP говорит, когда начал работу (%VBACKUP-I-STARTED),
итоги и чем и за сколько закончил (%VBACKUP-I-COMPLETED). Листинг сам
по себе ответ и ничего такого не пишет.

## /CONFIRM -- спрашивать перед каждым файлом

Спрашивает на терминале перед каждым файлом: YES, NO, QUIT или ALL.
Пустой ответ -- NO.

## /REPLACE -- перезаписывать существующее

При сохранении: существующий saveset перезаписывается.

При восстановлении: существующий файл удаляется и восстанавливается
заново. Без /REPLACE он остаётся, и вы видите %VBACKUP-W-FILEEXISTS.

При извлечении: существующий выходной файл перезаписывается.

## /OWNER -- кому принадлежат восстановленные файлы

```
/OWNER=ORIGINAL
/OWNER=DEFAULT
/OWNER=пользователь
```

ORIGINAL возвращает файлы их владельцам: по имени, если такое имя есть
на этой машине, иначе по номеру. Так по умолчанию для root.

DEFAULT оставляет файлы вам. Так по умолчанию для всех остальных --
отдать файл другому они всё равно не могут.

пользователь -- все файлы отдаются ему.

## /LIST -- листинг saveset-а

```
/LIST[=файл]
```

Показывает, что лежит в saveset-е: сначала сводку (кто записал, когда,
какой командой), затем файлы. С именем файла листинг пишется в файл.

Список читается из каталога в конце saveset-а, поэтому даже очень
большой saveset показывается сразу.

/LIST можно дать и при сохранении -- будет показан новый saveset.

## /BRIEF -- краткий листинг

Имя, размер и дата каждого файла. Так по умолчанию.

## /FULL -- подробный листинг

Добавляет тип, владельца, права, контрольную сумму и состояние каждого
файла.

## /FORMAT -- вид листинга

```
/FORMAT=VMS   (по умолчанию)
/FORMAT=LS
```

LS -- по строке на файл, как "ls -l", с полным хранимым именем. Для
чтения программами.

## /EXTRACT -- достать один файл

```
/EXTRACT=хранимое-имя
```

Пишет содержимое одного файла в выходную спецификацию или в
стандартный вывод. Имя точное, без шаблонов; /LIST его показывает.
Файл находится через каталог, поэтому это быстро даже в большом
saveset-е.

```
$ vbackup home.bck /EXTRACT=rrl/notes.txt | less
```

## /COMPARE -- сравнить saveset с диском

Читает saveset и сравнивает каждый файл с диском: тип, размер,
содержимое, цель символической ссылки. Различие сообщается как
%VBACKUP-E-COMPARERR, код завершения 2.

## /RECORD -- запомнить, что сохранено

При сохранении: когда saveset записан (а с /VERIFY -- и проверен),
журнал запоминает saveset и для каждого файла, сохранённого без
происшествий, его размер, времена и inode. Следующий /SINCE=BACKUP
сохранит только изменившееся. Файл, который менялся во время сохранения
или не прочитался, не запоминается -- в следующий раз он сохранится
снова.

С saveset-ами и без выхода (vbackup a.bck,b.bck /RECORD): журнал
восстанавливается из их каталогов. Нужно, если журнал потерян.

## /JOURNAL -- какой журнал

```
/JOURNAL[=файл]
```

Журнал -- /var/lib/vbackup/vbackup.jnl для root и
~/.vbackup/vbackup.jnl для остальных. /JOURNAL=файл -- другой журнал,
например свой для каждого плана резервного копирования.

С /LIST и без параметров журнал показывается: какие saveset-ы он знает.
/FULL добавляет файлы и где их последняя копия; /SELECT отбирает файлы
по абсолютному имени:

```
$ vbackup /JOURNAL /LIST /FULL '/SELECT=*/notes.txt'
```

## /INCREMENTAL -- восстановить цепочку saveset-ов

```
$ vbackup full.bck,mon.bck,tue.bck /home /INCREMENTAL
```

Восстанавливает полный saveset, затем каждый инкрементальный, от старых
к новым, и приводит каждый каталог к виду на момент последнего
сохранения: файл, которого более поздний saveset уже не перечисляет,
удаляется. Изменившиеся файлы заменяются -- /INCREMENTAL включает
/REPLACE.

Чистятся только каталоги, которые есть в saveset-е, и никогда сам
выходной каталог. Saveset без каталога или сделанный VBACKUP до X01-02
не принимается (%VBACKUP-E-NOTINCR): по неполному списку ничего не
удаляется. /CONFIRM спрашивает перед каждым удалением, /LOG сообщает о
нём. /SELECT и /EXCLUDE вместе с /INCREMENTAL не принимаются: чистка
задела бы каталоги, которые вы не собирались трогать.

Заметьте: BACKUP в OpenVMS восстанавливает инкрементальную цепочку от
новых к старым; VBACKUP -- от старых к новым.

## /HELP -- показать это описание

```
vbackup /HELP [тема ...]
```

Показывает тему этого описания, например vbackup /HELP /VERIFY.

## Шаблоны -- как раскрывается спецификация файла

```
*      любые символы в одном имени
% ?    один символ
...    любое число уровней каталогов, в том числе ни одного
```

База спецификации -- часть до первого шаблона. Хранимые имена
отсчитываются от неё:

```
/home/rrl                база /home          имена rrl, rrl/...
/home/rrl/src/.../*.c    база /home/rrl/src  имена a.c, lib/b.c
/etc/*.conf              база /etc           имена host.conf, ...
```

Подходящий каталог берётся со всем содержимым. Скрытые файлы (имена с
точки) тоже подходят.

## Инкременты -- сохранять только изменённое

Один раз сделайте полный saveset с /RECORD, потом -- инкрементальные:

```
$ vbackup /home full.bck /RECORD
$ vbackup /home mon.bck /SINCE=BACKUP /RECORD
$ vbackup /home tue.bck /SINCE=BACKUP /RECORD
```

Каждый инкрементальный saveset содержит только файлы, изменившиеся с
последнего /RECORD, но его каталог перечисляет все файлы, какие были, --
поэтому восстановление знает, что удалено. Восстанавливайте все по
порядку:

```
$ vbackup full.bck,mon.bck,tue.bck /restore /INCREMENTAL
```

Что охвачено и что сохранено: /SELECT, /EXCLUDE, флаг nodump,
/NOCROSS_DEVICE и /BY_OWNER говорят, о каких файлах saveset; /SINCE,
/BEFORE и /SINCE=BACKUP -- какие из них сохраняются.


## Scheduling -- регулярные сохранения и ротация, через BATCH

VBACKUP не планирует себя и не удаляет старые saveset-ы: это дело
пакетной очереди, и BATCH (подсистема пакетных заданий, `batch submit`)
делает это так, как принято в OpenVMS, -- задание выполняет сохранение и
ставит само себя в очередь на следующий день.

```sh
#!/bin/sh
# /opt/jobs/vbackup-daily.sh - полная копия в воскресенье, инкремент в остальные дни
T=/backup/home-$(date +%Y%m%d)
if [ "$(date +%u)" = 7 ]; then
	vbackup /home $T.bck /RECORD /VERIFY
else
	vbackup /home $T.bck /SINCE=BACKUP /RECORD /VERIFY
fi
# Ротация: хранятся пять недель saveset-ов
find /backup -name 'home-*.bck*' -mtime +35 -delete
# Снова завтра в 02:00 - задание ставит себя в очередь само
batch submit "$0" /NAME=vbackup-daily "/AFTER=$(date -d tomorrow +%d-%b-%Y:02:00 | tr a-z A-Z)"
```

```
$ batch submit /opt/jobs/vbackup-daily.sh /NAME=vbackup-daily /AFTER=TOMORROW
```

Задание, завершившееся с ошибкой, остаётся в очереди вместе с журналом
(`batch show`), где есть сообщения VBACKUP и код завершения; ничего не
теряется молча, как с cron.
## OpenVMS -- saveset-ы, записанные OpenVMS BACKUP

Saveset, записанный OpenVMS BACKUP, тоже читается: скопируйте его сюда
в двоичном режиме (FTP "binary" или побайтная копия файла с ленты) и
дайте на вход. VBACKUP узнаёт его по первому блоку и говорит
VMSSAVESET.

```
$ vbackup USERS.BCK /LIST                то, что показывает BACKUP/LIST
$ vbackup USERS.BCK /LIST /FULL          то, что показывает BACKUP/LIST/FULL
$ vbackup USERS.BCK /restore/vms         файлы -- в /restore/vms
$ vbackup USERS.BCK /restore/vms /SELECT=*.COM
$ vbackup USERS.BCK "/EXTRACT=[SMITH]LOGIN.COM;3" login.com
$ vbkx x USERS.BCK -C /restore/vms       то же через vbkx (и vbkx.exe)
```

Листинг -- собственный листинг BACKUP, строка в строку. При
восстановлении имена становятся именами Linux: [SMITH.WORK]NOTES.TXT;5
-- это SMITH/WORK/NOTES.TXT в выходном каталоге; старшая версия
получает простое имя, младшие сохраняют ";n" (NOTES.TXT;4).
Экранирование ODS-5 снимается (^_ -- пробел, ^. -- точка). /SELECT,
/EXCLUDE и /EXTRACT принимают имена Linux; /EXTRACT ещё и имя с ";n"
или имя VMS, как его показывает листинг.

Текстовые файлы -- записи переменной длины, VFC, фиксированные с
управлением кареткой, потоковые форматы -- становятся текстами с LF,
как их делает FTP VMS. Программы, объектные файлы и прочие файлы без
управления кареткой копируются как лежат на диске VMS. Индексные и
относительные файлы копируются образом файла RMS (VMSRAW): их записи
без RMS не достать. Режим берётся из защиты (R -- r, W -- w; E только
у каталогов), время -- из даты ревизии; владелец -- тот, кто
восстанавливает.

Плохие блоки восстанавливаются по XOR-блокам /GROUP_SIZE, как это
сделал бы BACKUP; файл, потерявший данные, называется FILDAMAGED. Не
читаются: saveset-ы, зашифрованные BACKUP (/ENCRYPT), и LBN-данные
saveset-ов /IMAGE и /PHYSICAL. /COMPARE, /INCREMENTAL, /ORIGINAL,
/IMAGE и /TRANSFER к такому saveset-у не применяются. Midnight Commander
открывает его, как saveset VBACKUP (через vbackup); MultiArc в far2l (он
узнаёт saveset по "VBKB" в начале, а BACKUP этого не пишет), модуль WCX
для Total и Double Commander и vbkx-go, vbkx-rs, vbkx-pl -- нет. Формат описан в doc/vmsbackup.md.

## Windows -- vbackup.exe, утилита в Windows

vbackup.exe -- это VBACKUP, собранный для Windows (MinGW-w64): та же
команда, те же saveset-ы. Saveset, сделанный в Linux, там листается,
восстанавливается и сравнивается; сделанный там читается в Linux и
vbkx. Собирается из этого дерева в Linux, когда есть MinGW-w64 и
исходники StarLet:

```
$ cmake -S . -B build-win -DCMAKE_TOOLCHAIN_FILE=cmake/mingw-w64.cmake \
        -DVBACKUP_STARLET_SRC=/root/Works/starlet-1.6.8
$ cmake --build build-win                vbackup.exe, vbkx.exe, units.exe
```

```
C:\> vbackup C:\Users\ivan\Documents D:\docs.bck /LOG
C:\> vbackup D:\docs.bck /LIST
C:\> vbackup D:\docs.bck C:\restore
C:\> vbackup C:\data D:\data.bck /ENCRYPT /KEY_FILE=C:\Users\ivan\backup.key
```

Имена -- в Юникоде (в saveset-е UTF-8), пути любой длины; разделяют и
"\", и "/" -- "\" где угодно в командной строке считается
разделителем, в /SELECT и /COMMENT тоже. Что сохраняется: данные, время
(изменения, доступа, смены атрибутов и создания), атрибуты (только
чтение, скрытый, системный, архивный, временный, не индексировать),
дескриптор безопасности (владелец, группа, DACL; у оператора резервного
копирования и SACL), альтернативные потоки данных (как расширенные
атрибуты "user.<поток>", до 64 КБ каждый), каталоги, жёсткие ссылки,
символьные ссылки и junction-ы (как ссылки), разреженные файлы с их
дырами. /LIST /FULL показывает атрибуты ("Windows: HIDDEN ARCHIVE") и
владельца как ДОМЕН\пользователь.

Запускайте vbackup.exe от имени администратора ("Запуск от имени
администратора"), чтобы сохранить все файлы и вернуть всё: тогда у него
привилегии оператора резервного копирования -- он читает файлы, на которые
у него нет прав, и /OWNER=ORIGINAL у него по умолчанию, так что владельцы
и ACL возвращаются как были. Пользователь не администратор восстанавливает
файлы как свои: они получают ACL каталога, в который попадают (задайте
/OWNER=ORIGINAL, чтобы получить сохранённый); /OWNER=пользователь и
/BY_OWNER там отвергаются. В Linux saveset из Windows
восстанавливается как любой другой; потоки становятся атрибутами "user.",
атрибуты Windows и ACL пропускаются.

При восстановлении имя, которое Windows не может хранить -- с ":",
"<>"|?*\", с точкой или пробелом в конце, CON, NUL, COM1 и подобные,
-- не создаётся, и об этом сказано (OPENOUT ... not a valid name on
Windows). Два имени, отличающихся только регистром, в Windows -- один
файл: второе не восстанавливается (FILEEXISTS; и с /REPLACE тоже:
OPENOUT ... differs in case only). FIFO и устройства из Linux-saveset-а
называются (UNSUPP). Из расширенных атрибутов Linux-saveset-а потоками
становятся только "user."; остальные пропускаются. Для символьной ссылки
нужно право создавать ссылки (администратор или режим разработчика
Windows 10/11).

Saveset на другом узле (node::file) идёт через ssh.exe -- клиент OpenSSH
из Windows 10/11 (другой называет VBACKUP_RSH). Нет в Windows: /PHYSICAL
и /IMAGE -- отвергаются сразу; упреждающего чтения файлов; теневых копий
(VSS) -- файл, занятый другой программой, сохраняется таким, каким его
удаётся прочитать, или называется. Права файла ключа не проверяются:
держите его в своём профиле, где читать его можете только вы. Журнал --
%USERPROFILE%\.vbackup\vbackup.jnl.

## Время -- как записывается время

```
dd-MMM-yyyy[ hh:mm[:ss]]   3-OCT-2026 14:00
hh:mm[:ss]                 сегодня в это время
-[dd ]hh:mm[:ss]           столько времени назад: "-1 0:0" -- сутки назад
TODAY  YESTERDAY  TOMORROW  NOW
BACKUP                     только /SINCE: с последнего /RECORD каждого файла
```

## Plugins -- saveset-ы в файловых менеджерах

Saveset-ы можно смотреть в файловых менеджерах как папки. Все плагины
только читают: можно заглянуть внутрь и скопировать файлы; saveset не
меняется. Список берётся из каталога, поэтому даже очень большой
saveset открывается сразу.

Midnight Commander: нажмите Enter на файле .bck или .sav -- или на saveset-е с любым именем: установка добавляет магию VBACKUP в /etc/magic, и MC узнаёт его по содержимому. Установка кладёт
скрипт uvbk в extfs MC и секцию [vbackup] в mc.ext.ini; вручную:
скопируйте share/vbackup/plugins/mc/uvbk в ~/.local/share/mc/extfs.d, а
секцию из mc.ext.ini.vbackup -- в свой mc.ext.ini перед [Default].
Многотомный saveset открывается только с локального диска.

far2l (Linux) и Far Manager 3 (Windows): MultiArc с описанием формата
share/vbackup/plugins/far/vbackup.ini (для far2l установка добавляет
его сама). Работу делает vbkx; на Windows положите vbkx.exe в PATH.
Enter или Ctrl+PgDn на saveset-е (он узнаётся по сигнатуре при любом имени); F5 копирует файлы.

Total Commander (Windows) и Double Commander (Linux): плагин архиватора
vbackup.wcx64 (64-битный TC) / vbackup.wcx (32-битный TC; на Linux -- для DC) -- установите его в настройках
плагинов и свяжите с расширением bck.

Зашифрованный saveset: файловые менеджеры не умеют спрашивать пароль.
Запишите его в файл ключа (chmod 600) и назовите этот файл в
переменной окружения VBACKUP_KEY_FILE до запуска файлового менеджера
(в Windows -- в системных настройках переменных среды). Без неё
saveset не откроется -- ответа на экране никто не ждёт.

## Vbkx -- автономный извлекатель

vbkx читает saveset-ы на машине, где VBACKUP не установлен. Это одна
статически собранная программа: скопируйте её туда и запускайте.

```
vbkx l saveset                          список файлов
vbkx x saveset [-C dir] [-f] [name...]  извлечь всё или названные файлы
vbkx p saveset name                     один файл на стандартный вывод
vbkx t saveset                          прочитать всё, проверить суммы
  ... -k keyfile                        зашифрованный saveset: пароль
  ... -n                                никогда не спрашивать его (для программ)
```

Имя -- сохранённое имя, как в списке; имя каталога берёт всё, что в
нём. -C задаёт выходной каталог (создаётся, если его нет); -f
перезаписывает существующие файлы.

vbkx восстанавливает данные, дыры, права, времена, символьные и жёсткие
ссылки, FIFO; от root ещё владельца (по номеру) и файлы устройств. ACL,
расширенные атрибуты и флаги chattr он не восстанавливает: если они
нужны, восстанавливайте через VBACKUP.

Повреждённый saveset чинится, насколько позволяют XOR-блоки. vbkx
называет каждый неполный файл ("is incomplete") и каждый файл, до
которого не добрался ("not extracted"). Код завершения: 0 --
готово; 1 -- что-то повреждено или не сделано; 2 -- команду или
saveset нельзя использовать.

Saveset, записанный OpenVMS BACKUP, берётся так же, по именам Linux
его файлов (см. тему OPENVMS).

Зашифрованный saveset: vbkx берёт пароль из -k keyfile, иначе из
VBACKUP_KEY_FILE, иначе спрашивает на терминале (в Windows -- в
консоли).

Есть и vbkx.exe для Windows, с теми же командами. Он восстанавливает
данные, времена, файлы только для чтения, каталоги и жёсткие ссылки;
символьные ссылки -- только где Windows их разрешает. Имя, которое
Windows не принимает (с : ? * и т.п., или CON, NUL ...), не
извлекается, и об этом сказано.

## Примеры

Сохранить домашний каталог, проверить, посмотреть:

```
$ vbackup /home/rrl /backup/rrl.bck /VERIFY
$ vbackup /backup/rrl.bck /LIST
```

Восстановить в другое место:

```
$ vbackup /backup/rrl.bck /tmp/restore
```

Сохранить только изменённое сегодня, томами по 4 ГБ:

```
$ vbackup /home /mnt/usb/home.bck /SINCE=TODAY /VOLUME_SIZE=4G
```

Восстановить только исходники на C, перезаписывая существующие:

```
$ vbackup /backup/rrl.bck /home '/SELECT=*.c' /REPLACE
```

Скопировать дерево на другой диск и проверить копию:

```
$ vbackup /home/rrl /mnt/disk2 /VERIFY
```

Отправить saveset на другую машину:

```
$ vbackup /etc - | ssh backup-host 'cat > etc.bck'
```

## Неполадки -- что делать, если

**Saveset не создаётся: %VBACKUP-E-OPENOUT ... errno: 17 (File
exists).** Saveset с таким именем уже есть. Дайте другое имя или
/REPLACE, чтобы перезаписать.

**%VBACKUP-E-IVOP, cannot tell what to do.** Вход -- не saveset, а
выход на saveset не похож. При сохранении дайте /SAVE_SET или имя с
окончанием .bck или .sav.

**%VBACKUP-E-MAXPARM, too many parameters: .log.** Квалификатор набран
без косой черты. Пишите /LOG, а не .log.

**В Windows: %VBACKUP-E-OPENOUT ... not a valid name on Windows.**
В saveset-е есть имя, которого в Windows не бывает: с ":" или "?",
с точкой или пробелом в конце, CON, NUL, COM1... Этот файл не
восстановлен, остальные -- да. Восстановите его в Linux или извлеките
под другим именем: /EXTRACT="a:b" ab.txt.

**В Windows: %VBACKUP-E-QUALUSE, Qualifier: /PHYSICAL - not on
Windows.** /PHYSICAL и /IMAGE работают только в Linux. Сохраните
файлы или сделайте это в Linux.

**%VBACKUP-W-XATTRSKIP.** Расширенный атрибут файла не сохранён: его
не удалось прочитать, или он длиннее 64 КБ. В Windows это альтернативный
поток данных длиннее 64 КБ. Сам файл сохранён. Если поток важен,
скопируйте его в отдельный файл или задайте /NOXATTRS.

**В Windows: %VBACKUP-W-ATTRERR ... security not restored.** Не удалось
назначить владельца файла: отдать файл другой учётной записи может только
администратор. Запустите vbackup.exe от имени администратора или
восстанавливайте без /OWNER=ORIGINAL -- тогда файлы ваши.

**В Windows: символьная ссылка не восстановлена (OPENOUT ... errno:
1).** Для ссылок нужно право: запустите от имени администратора или
включите режим разработчика Windows (Параметры, Для разработчиков).

**%VBACKUP-E-WRONGKEY.** Пароль не открывает saveset. Проверьте файл
ключа: считается только первая строка, регистр букв важен. Ничего не
записано. Saveset с потерянным паролем не откроет никто.

**%VBACKUP-E-NOKEY.** Saveset зашифрован, а спросить негде (cron, канал,
файловый менеджер). Дайте /KEY_FILE=файл или задайте VBACKUP_KEY_FILE.

**%VBACKUP-E-KEYFILE ... chmod 600 it.** Файл ключа могут читать
другие. Сделайте его только своим: chmod 600 файл.

**%VBACKUP-W-BLKFORGED.** Блок зашифрованного saveset-а не тот, что был
записан, хотя контрольная сумма верна: его изменили нарочно, или
носитель ведёт себя очень странно. Если следом идёт BLKFIXED -- блок
починен и файлы верны; выясните, кто мог писать в saveset.

**Зашифрованный saveset открывается несколько секунд.** Это намеренная
цена PBKDF2 (600000 итераций) -- её платит и каждая попытка
подбора. Около 0,5 с на ПК, 1,6 с на маленькой ARM-плате с инструкциями
SHA, 6 с без них. VBACKUP_KDFITER -- для тестов; для настоящих
saveset-ов не уменьшайте.

**%VBACKUP-I-BLKFIXED при восстановлении.** Блок saveset-а был
испорчен и исправлен. Все файлы в порядке. Возможно, носитель
умирает: скопируйте saveset на другой.

**%VBACKUP-W-PARITYERR.** Saveset сделан с /PARITY: блоки группы были
плохими, а её блоки чётности не сошлись с восстановленным -- какой-то
блок группы с верной контрольной суммой содержит другие байты (записан
неверно или изменён нарочно). Ничего из этой группы по чётности не
восстанавливается; её файлы названы FILDAMAGED. Сохраните saveset:
остальные группы в порядке.

**%VBACKUP-E-NOTSAVESET для saveset-а, сделанного с /PARITY.** Он
формата версии 2: VBACKUP или vbkx до X01-14 его не читают. Возьмите
X01-14 или новее.

**%VBACKUP-E-BLKLOST и %VBACKUP-E-FILDAMAGED.** Блоки потеряны и не
могут быть исправлены. Файлы, названные в FILDAMAGED, неполные;
файлы, названные в FILLOST, не восстановлены вовсе; все остальные в
порядке. В следующий раз дайте /PARITY=2 или больше (чинятся несколько
плохих блоков группы), меньший /GROUP_SIZE или храните две копии важных
saveset-ов.

**%VBACKUP-W-UNNAMED.** Блоки потеряны, а каталога у saveset-а нет или
он тоже повреждён. Каких-то файлов в выходном каталоге может не быть,
и VBACKUP не может назвать их все. Сравните результат с источником
или с /LIST более старого saveset-а.

**%VBACKUP-E-MISSVOL.** Не хватает тома. Сложите все тома в один
каталог, не меняя имён.

**%VBACKUP-W-NOTRAILER.** Сохранение не завершилось (кончилось место,
программу остановили) или нет последнего тома. Файлы до места обрыва
восстанавливаются. /LIST работает медленнее -- читает весь saveset.

**%VBACKUP-W-FILCHANGED при сохранении.** В файл писали во время
сохранения; копия может быть смесью старого и нового. Сохраните его,
когда никто не пишет, или со снапшота.

**%VBACKUP-W-ATTRERR при восстановлении.** Не удалось поставить
владельца, права, время, атрибут или флаг. Чаще всего -- вы не root:
восстанавливайте под root или дайте /OWNER=DEFAULT.

**%VBACKUP-E-OPENOUT ... a name that leads out of the output
directory.** В saveset-е есть имя с ".." или с "/" в начале, или имя,
идущее через символическую ссылку. Такой файл никогда не пишется.
Saveset сделан не VBACKUP-ом или сделан во вред.

**/SINCE=BACKUP сохраняет всё.** Журнал не знает этих файлов:
сохранения делались без /RECORD, с другим /JOURNAL или от другого
пользователя (у каждого свой журнал). Посмотрите vbackup /JOURNAL /LIST.

**%VBACKUP-E-NOTINCR.** /INCREMENTAL нужен saveset с каталогом,
сделанный VBACKUP X01-02 или новее. Такой восстанавливайте без
/INCREMENTAL.

**%VBACKUP-W-MISSING.** Файл должен был остаться от более раннего
saveset-а цепочки, а его нет. Чаще всего пропущен saveset цепочки: дайте
все, от старых к новым.

**%VBACKUP-E-JNLERR.** Журнал не читается или не пишется -- причина в
сообщении. Испорченный журнал можно восстановить: удалите его и дайте
saveset-ы с /RECORD.

**Из каталога ничего не сохраняется.** Проверьте флаг nodump:
lsattr -d каталог. /IGNORE=NOBACKUP -- сохранить всё равно.

**Сохранение идёт медленно, или нужно понять, не виноват ли поток
записи.** Saveset пишет отдельный поток, пока читаются файлы. Задайте в
окружении VBACKUP_PIPELINE=0, чтобы писать без этого потока:
VBACKUP_PIPELINE=0 vbackup /home h.bck. Выключается только поток,
подсказки кэшу страниц остаются. Saveset получится тот же. Если
проблема ушла, сообщите о ней.

Ещё восемь потоков заранее читают следующие файлы, пока сохраняется
или копируется текущий, чтобы сохранение находило их в кэше.
VBACKUP_PREFETCH=n задаёт число потоков, 0 выключает опережающее
чтение. На NFS или медленном сетевом диске может помочь больше потоков,
на одном медленном жёстком диске -- меньше.

**Saveset с OpenVMS -- "не saveset", или с него делается копия.** Он
скопирован в текстовом режиме или с другим форматом записей: FTP нужен
в двоичном режиме ("binary", "type image"). Saveset, снятый с ленты,
должен сохранить размер блока. Размер правильной копии кратен размеру
блока, который показывает BACKUP/LIST.

**В тексте с OpenVMS перед каждой строкой счётчик байтов.** На VMS у
файла нет управления кареткой (сделайте там SET FILE/ATTRIBUTE=RAT:CR
или CONVERT), поэтому VBACKUP скопировал его как есть, со счётчиками
записей.

**%VBACKUP-I-VMSRAW для индексного файла.** Его записям нужен RMS.
Восстановите его, скопируйте обратно на VMS в двоичном режиме и
сделайте SET FILE/ATTRIBUTE, или перед сохранением сделайте на VMS
CONVERT в последовательный файл.

**После сохранения файлов нет в кэше страниц.** Так задумано. VBACKUP
выбрасывает из кэша страницы saveset-а, который пишет или читает, и
страницы файла, которого в кэше не было до чтения. Файлы, которые были
в кэше, там и остаются.

```
%VBACKUP-I-VMSSAVESET   на входе saveset OpenVMS BACKUP: его размер блока и группы
%VBACKUP-I-VMSNOCRC     ... записан с /NOCRC: порча в его блоках не видна
%VBACKUP-I-VMSRAW       ... индексный или относительный файл восстановлен образом RMS
%VBACKUP-W-PARITYERR    /PARITY: чётность группы не сошлась, ничего из неё не восстановлено
%VBACKUP-W-XATTRSKIP    расширенный атрибут (в Windows -- поток) не сохранён: не читается или больше 64 КБ
```

Сообщения идут в стандартный поток ошибок. В начале -- дата, время и
номер процесса:

```
03-10-2026 15:22:19.109 3715297 %VBACKUP-I-RESTORED, out/tree restored
```
