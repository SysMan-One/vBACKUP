# vBACKUP - проектный документ

Статус: этапы 1-6 реализованы (X01-06, 5-OCT-2026).

Цель: утилита резервного копирования для Linux, по удобству и модели
работы близкая к OpenVMS BACKUP: одна команда `вход выход /квалификаторы`,
saveset в своём формате с контролем целостности и восстановлением битых
блоков, отбор файлов по шаблонам и датам, сравнение, проверка, инкременты.

Внешние зависимости: только libc, StarLet (CLI$, $PUTMSG/FAO, CRC-32,
pattern_match, bintim) и HELP (библиотека справки).  Всё остальное -
своё.  Совместимость с tar не требуется.  Лента не поддерживается.


## 1. Принятые решения

| # | Вопрос | Решение |
|---|---|---|
| 1 | Формат | Свой: блоки фиксированного размера с заголовком и CRC-32, внутри поток TLV-записей, XOR-группы в потоке |
| 2 | Совместимость с tar | Не нужна.  Вместо неё - спецификация формата (`doc/format.md`) и автономный извлекатель на одной libc (этап 3) |
| 3 | Лента | Нет.  Носитель - файл (или stdout) |
| 4 | Нарезка на тома | Обязательна: `/VOLUME_SIZE=` |
| 5 | Шифрование | **Сделано на этапе 6 (X01-06), без libcrypto**: ChaCha20 + HMAC-SHA256, ключи PBKDF2-HMAC-SHA256, свои реализации по RFC (раздел 17).  libcrypto через dlopen отвергнута: автономный vbkx (статический, Windows), WCX-плагин и распаковщики для гиков должны читать зашифрованный saveset без чего-либо ещё |
| 6 | Сжатие | Позже (этап 4, свой кодек формата LZ4-block), по DATA-записям |
| 7 | `/RECORD` | Журнал (файл состояния), не xattr на исходных файлах |
| 8 | Размеры по умолчанию | `/BLOCK_SIZE=65536`, `/GROUP_SIZE=10` |
| 9 | Порядок байт на носителе | little-endian, явное кодирование полей (никаких записей struct "как есть") |
| 10 | Номер facility сообщений | `VBACKUP$K_FACNO 0x0112` (0x0110 HELP, 0x0111 SEARCH) |
| 11 | Чтение saveset-а | Отдельное ядро `libvbkrd`: им пользуются vbackup, автономный извлекатель и (этап 5) плагины - одна реализация чтения.  До этапа 5 оно линкуется со StarLet; CRC и вызовы ОС идут через один заголовок-прокладку `lib/vbkos.h`, так что для Windows на этапе 5 меняется один файл, а не библиотека |
| 12 | Файловые менеджеры | MC, Far, Total Commander, Double Commander - только чтение, **отложено** (этап 5); сейчас только ядро, но каталог и `libvbkrd` сразу делаются так, чтобы плагины потом легли без переделки |

Почему журнал, а не xattr (п.7):

- бэкап не должен писать в исходные файлы: только-чтение ФС, снапшоты,
  NFS с root_squash - xattr туда не записать;
- запись xattr меняет ctime файла, то есть сама создаёт "изменение" -
  для ctime-ориентированных инструментов (и для нашего же инкремента)
  все файлы выглядели бы изменёнными;
- не каждая ФС держит user.* xattr (vfat, exfat, часть NFS);
- журнал всё равно нужен для `/JOURNAL` (в каком saveset-е лежит файл)
  и для цепочки инкрементов;
- журнал всегда можно **восстановить из каталогов saveset-ов** - в них
  есть всё, что в него пишется.  Потеря журнала - не катастрофа.


## 2. Синтаксис команды

    vbackup input-spec[,...] output-spec [/qualifiers]

Операция определяется по сторонам, как у BACKUP:

| Вход | Выход | Операция |
|---|---|---|
| файлы | saveset (`/SAVE_SET`, расширение `.bck` или `-`) | сохранение |
| saveset (опознаётся по magic в первом блоке) | каталог | восстановление |
| saveset | нет, `/LIST[=file]` | листинг |
| saveset | каталог, `/COMPARE` | сравнение saveset-а с диском |
| файлы | каталог | копирование диск->диск (этап 2) |

CLI$ из StarLet не знает позиционных квалификаторов (`x.bck/SAVE_SET` у
VMS), поэтому saveset на входе опознаётся по содержимому, а на выходе -
по `/SAVE_SET`, по расширению `.bck` или по `-` (stdout).

### Входная спецификация и хранимые имена

- Каталог без шаблона - всё дерево, сам каталог входит в имена
  (`/home/rrl` -> имена `rrl/...`, база `/home`).
- Шаблоны `*`, `%`, `?` - в пределах одного уровня.
- `...` - рекурсия, аналог `[...]`: `/home/rrl/src/.../*.c`.
- База - неизменная часть спецификации до первого шаблона или `...`;
  хранимое имя - путь относительно базы.  Базы всех входных спецификаций
  пишутся в SUMMARY.
- Восстановление: файлы ложатся под `output-dir/<хранимое имя>`.

### Квалификаторы (этапы 1-3)

Сохранение:

| Квалификатор | Смысл |
|---|---|
| `/SAVE_SET` | выход - saveset |
| `/BLOCK_SIZE=n` | размер блока, 8K..1M, по умолчанию 64K |
| `/GROUP_SIZE=n` | XOR-блок на каждые n блоков данных, 0 - без чётности, по умолчанию 10 |
| `/VOLUME_SIZE=size` | нарезка на тома (`4G`, `700M`); без него - один том |
| `/COMMENT="..."` | комментарий в SUMMARY |
| `/SELECT=(pat,...)` `/EXCLUDE=(pat,...)` | отбор по хранимому имени |
| `/SINCE=time` `/BEFORE=time` | отбор по времени; `time` в формате `__util$bintim`, этап 2: `BACKUP` |
| `/MODIFIED` `/CREATED` `/CHANGED` | к какому времени относятся `/SINCE`, `/BEFORE`: mtime (по умолчанию), btime (statx - настоящее время создания на ext4/xfs/btrfs), ctime |
| `/BY_OWNER=user` | только файлы владельца |
| `/[NO]CROSS_DEVICE` | заходить ли в другие ФС (по умолчанию нет - как BACKUP одного устройства) |
| `/IGNORE=NOBACKUP` | сохранить и файлы с флагом `chattr +d` (nodump) - аналог NOBACKUP у VMS; без него они пропускаются |
| `/[NO]XATTRS` | сохранять xattr, ACL, capabilities, метку SELinux (по умолчанию да) |
| `/VERIFY` | после записи перечитать saveset и сравнить с диском |
| `/RECORD` `/JOURNAL[=file]` `/INCREMENTAL` | этап 2 |

Восстановление: `/SELECT`, `/EXCLUDE`, `/REPLACE` (перезаписать
существующие; без него - `%VBACKUP-W-FILEEXISTS` и пропуск, как у VMS
без `/NEW_VERSION`), `/OWNER=ORIGINAL|DEFAULT|user` (у root по умолчанию
ORIGINAL, у остальных DEFAULT), `/[NO]XATTRS`, `/INCREMENTAL` (этап 2).

Общие: `/LOG`, `/CONFIRM`, `/LIST[=file]` с `/FULL` или `/BRIEF`,
`/COMPARE`, `/HELP [topic]`.

Для файловых менеджеров (раздел 8):

| Квалификатор | Смысл |
|---|---|
| `/LIST/FORMAT=LS` | листинг из каталога в формате `ls -l`, полные хранимые имена, `-> цель` у ссылок, дата `MM-DD-YYYY hh:mm:ss` - то, что ждёт extfs MC и MultiArc Far |
| `/EXTRACT=stored-name` | одно содержимое файла по точному имени (без шаблонов) в выходной файл или в `-` (stdout); переход к нему по каталогу, без чтения потока |


## 3. Формат saveset-а

Точное описание - **`doc/format.md`**, единственный источник истины о
байтах на носителе; здесь только суть.

- Тома: `x.bck`, `x.bck.002`, ...; каждый начинается с VHDR (копия
  SUMMARY), последний кончается TRAILER (где каталог, итоги).
- Блоки фиксированного размера (8K..1M, по умолчанию 64K): заголовок 64
  байта с CRC-32 (IEEE, это и считает `__util$crc32c` StarLet - несмотря
  на имя, не Castagnoli), сквозной номер, `recoff` - точка
  ресинхронизации.
- XOR-группы: после n блоков данных - XOR их payload-ов.  Заголовок
  потерянного блока восстанавливается из соседей: изменчивые поля
  (`recoff`, `paylen`) каждый блок дублирует о предыдущем блоке группы.
- Поток записей: SUMMARY, (FILE, DATA..., FEND) на файл, CATALOG, END.
  Атрибуты - TLV с единым пространством тегов; незнакомое пропускается по
  длине.  DATA несёт fileno и смещение - отсюда разреженные файлы без
  карты и точный отчёт о повреждённом файле после ресинхронизации.
- Каталог самодостаточен (листинг, переход к файлу по том/блок/смещение).
- Чтение: режим каталога (`/LIST`, `/SELECT`, `/EXTRACT`) и
  последовательный (полное восстановление, повреждённый или оборванный
  saveset без TRAILER).

## 4. Устройство программы

### 4.1 Конвейер сохранения

```
 обход дерева   ->  чтение файла   ->  поток записей  ->  блоки, XOR-группы, тома
 (vbkwlk: отбор,    (vbkatr: statx,     (vbkfmt: TLV,      (vbkwrt: BHDR, CRC-32,
  шаблоны, ...,      xattr, флаги,       little-endian)     VHDR, TRAILER, нарезка)
  /SINCE)            SEEK_DATA)
                                    \-> каталог спулится во временный файл (vbksav), пишется в конце
```

Этап 1 - один поток.  Конвейер разрезан на интерфейсы так, чтобы на
этапе 3 чтение файлов и запись блоков разнести по потокам (pthreads) без
переделки.

### 4.3 Порядок применения атрибутов при восстановлении

1. Создать объект (файл, каталог, ссылку, fifo, устройство).
2. Данные (для REG).
3. Владелец (`lchown`) - до режима, т.к. chown сбрасывает setuid/setgid.
4. Режим (`chmod`).
5. xattr и ACL (ACL после chmod, иначе chmod перетрёт маску).
6. Времена (`utimensat`); для каталогов - в самом конце, обратным
   порядком, иначе создание содержимого их перетрёт.
7. Флаги chattr (immutable, append-only) - последними, иначе в файл
   больше не записать.

## 8. Файловые менеджеры (только чтение) - этап 5, сделано

Решено на этапе 5: Far - оба (far2l и Far3, одно описание MultiArc);
Total Commander - 32 и 64 бит.  8.1 и 8.2 - сделано (`plugins/mc`,
`plugins/far`), 8.3 - сделано (`plugins/wcx`).

```
                       +-------------------- libvbkrd (C99, только libc) ----------------------+
                       |  тома, блоки, CRC-32, XOR, записи, каталог, извлечение по каталогу      |
                       +--------+-------------------+-------------------+---------------------+
                                |                   |                   |
                         vbackup (Linux)       vbkx / vbkx.exe     vbkwcx (.wcx/.wcx64/.so)
                          |          |              |                   |            |
                   MC extfs uvbk   far2l       Far3 MultiArc      Total Commander   Double Commander
                   (sh-скрипт)    MultiArc      (Windows)           (Windows)        (Linux)
```

Общее требование ко всем: листинг строится **из каталога** (TRAILER ->
CATALOG), извлечение одного файла - переходом по `volno/blkno/offset` из
каталога.  Поток целиком не читается ни при открытии, ни при F3/F5 одного
файла, поэтому saveset в сотни гигабайт открывается мгновенно.

Запись (copyin, rm, mkdir) не поддерживается: saveset неизменяем, как у
BACKUP.  Плагины возвращают "не поддерживается".

### 8.1 Midnight Commander (4.8.29) - сделано

- `uvbk` - POSIX sh, ставится в `extfs.d` (системный `/usr/lib/mc/extfs.d`
  или `~/.local/share/mc/extfs.d`).
- `list ARCHIVE` -> `vbackup ARCHIVE /LIST/FORMAT=LS`.
- `copyout ARCHIVE NAME TARGET` -> `vbackup ARCHIVE TARGET /EXTRACT=NAME`.
- Регистрация - секция в `mc.ext.ini` перед `[Default]`:

      [vbackup]
      Shell=.bck
      ShellIgnoreCase=true
      Open=%cd %p/uvbk://
      View=%view{ascii} vbackup %f /LIST/FULL

  Пользовательский `~/.config/mc/mc.ext.ini` в 4.8.29 заменяет системный
  целиком, поэтому установка правит системный (или печатает инструкцию).
- Ограничение: если saveset открыт внутри другого VFS, MC отдаёт скрипту
  временную копию без имени (`/tmp/f43513254`) - соседние тома тогда не
  найти.  Многотомный saveset открывается только с локального диска.

### 8.2 Far - сделано (MultiArc; родной плагин Far3 не понадобился)

- far2l (Linux) и Far3 (Windows) - MultiArc с описанием формата
  (`vbackup.ini`): команды листинга и извлечения плюс шаблон разбора
  строк листинга.  На Linux команды - `vbackup`, на Windows - `vbkx.exe`.
  Кода нет, только описание.
- Если MultiArc окажется мало (Far3 по умолчанию идёт с ArcLite, MultiArc
  ставится отдельно) - родной плагин Far3 поверх `libvbkrd` (этап 3b).

### 8.3 Total Commander и Double Commander - сделано (X01-05)

- WCX packer-плагин: `GetPackerCaps` (только чтение, `PK_CAPS_MULTIPLE`,
  `PK_CAPS_BY_CONTENT`), `CanYouHandleThisFile` (magic `VBKB`),
  `OpenArchiveW`, `ReadHeaderExW`, `ProcessFileW`, `CloseArchive`,
  `SetProcessDataProcW` (прогресс), `SetChangeVolProcW` (недостающий том).
- `ReadHeaderExW` идёт по каталогу, `ProcessFileW` с PK_EXTRACT
  переходит к файлу по каталогу, с PK_SKIP ничего не читает.
- Отображение: имена UTF-8 -> UTF-16, `/` -> `\`; время в нс -> FILETIME;
  атрибуты: каталог, readonly (нет w у владельца), hidden (имя с точки);
  symlink, устройства, fifo - показываются, при извлечении пропускаются
  (symlink - по желанию как файл-ссылка); размер u64 через
  `PackSizeHigh/UnpSizeHigh`.
- Сборка: `gcc-mingw-w64` (i686 и x86_64) из toolchain-файла - зависимость
  только сборки, не времени работы.  Тот же исходник собирается на Linux
  как .so для Double Commander - на нём и проверяется ABI без Windows.
- Проверка: `test/wcx_harness.c` загружает плагин (`dlopen`, под wine -
  `LoadLibrary`) и проходит OpenArchive/ReadHeader/ProcessFile на
  тестовом saveset-е, сравнивая результат с `vbackup /EXTRACT`.

Как сделано (`plugins/wcx/vbkwcx.c`, шапка - руководство):

- Экспорт полный: `OpenArchive(W)`, `ReadHeader`, `ReadHeaderEx(W)`,
  `ProcessFile(W)`, `CloseArchive`, `SetChangeVolProc(W)`,
  `SetProcessDataProc(W)`, `GetPackerCaps`, `CanYouHandleThisFile(W)`.
  Структуры и константы WCX описаны в самом файле; `__stdcall` и
  `--kill-at` на Windows, `WCHAR` = `uint16_t` на Linux.  Всё состояние -
  в контексте архива; общие только колбэки "для всех архивов" (handle -1).
- Время - DOS-время (в Ex-структурах WCX поля FILETIME нет); при
  извлечении файлу ставятся mtime/atime с наносекундами (FILETIME на
  Windows).  Атрибуты: 0x10, 0x01 (нет w у владельца), 0x02 (имя с точки).
- Без каталога (TRAILER потерян) или с дырой в каталоге - листинг по
  потоку, как у vbkx; если в потоке были потери, листинг кончается
  `E_BAD_DATA`, а не `E_END_ARCHIVE` - файл, чья FILE-запись пропала, не
  теряется молча.  Извлечение - по LOC с проверкой FILENO; DATA, DATAZ,
  дыры; CRC не сошлась или записи потеряны - `E_BAD_DATA`.
- Жёсткая ссылка без первого имени получает его данные (по каталогу, а
  без каталога - возвратом к первому имени в потоке).
- Символьные ссылки: на Linux (DC) создаются - в `CloseArchive`, после
  всех файлов; путь к файлу проходится по компоненту `openat(O_NOFOLLOW)`,
  так что ссылка (своя из прошлого запуска или чужая) не выводит за цель.
  На Windows пропускаются, как устройства, FIFO и сокеты.  Имена с `..`,
  ведущим `/`, `\`, а на Windows и недопустимые там (`c:`, `con`, `x?`)
  не показываются вовсе.
- Тома: соседние находит ядро; недостающий в середине и - без TRAILER -
  следующий за последним спрашиваются через ChangeVolProc
  (`vbk$rd_addvol`); отказ - файлы с записями там дают `E_BAD_DATA`.
- `.so` для DC собирается без StarLet (`VBK_NOSTARLET` в `lib/vbkos.h`:
  StarLet - статическая библиотека не PIC); разделитель имён на Linux -
  `/` (предположение: DC на Linux сам работает с `/`; DC здесь не стоит).
- Проверка `test/wcx.sh`: обычный, сжатый, многотомный, без каталога;
  спрошенный том (средний и последний); разреженный файл, жёсткая
  ссылка, кириллица с пробелом; одна порча на группу - всё цело, две -
  названо; подделка - за пределы цели ничего, и в два запуска тоже.
  `ctest`: `wcx` всегда, `wcxwin` (`.wcx64`, `.wcx`) при MinGW и wine;
  32-битный проходит только при wine с i386.


## 9. Этап 2 - журнал, инкременты, копирование

Байты на носителе - `format.md` (6.4, 6.5, 6.6, раздел 9); здесь команды
и поведение.

### 9.1 Что охвачено и что сохранено

- **Охват** задают фильтры по именам: `/SELECT`, `/EXCLUDE`, nodump,
  `/NOCROSS_DEVICE`, а также `/BY_OWNER`.
- **Что сохранить** внутри охвата решают фильтры по времени: `/SINCE`,
  `/BEFORE`, `/SINCE=BACKUP`.  Есть такой фильтр - saveset INCREMENTAL,
  и его каталог перечисляет весь охват: сохранённое со статусом,
  остальное как PRESENT.  Нет - saveset FULL, PRESENT-записей нет.
- Восстановление `/INCREMENTAL` удаляет только то, чего нет в охвате, и
  только внутри каталогов, которые сами есть в каталоге saveset-а.

### 9.2 Команды

| Команда | Что делает |
|---|---|
| `vbackup /home h.bck /RECORD` | сохранение + запись в журнал состояния каждого файла, сохранённого со статусом OK |
| `vbackup /home h1.bck /SINCE=BACKUP /RECORD` | инкремент: только изменённое с последней записи в журнал; остальное - PRESENT |
| `vbackup h.bck,h1.bck,h2.bck /r /INCREMENTAL` | восстановление цепочки по порядку (полный, затем инкременты - обратно порядку VMS, сознательно); после каждого saveset-а удаляется исчезнувшее |
| `vbackup h.bck,h1.bck /RECORD` | восстановить журнал из каталогов saveset-ов |
| `vbackup /JOURNAL /LIST [/FULL] [/SELECT=...]` | что записано в журнале: saveset-ы; с `/FULL` - файлы и где их последняя копия |
| `vbackup /home /mnt/copy` | копирование диск->диск (выход - не saveset): тот же код создания, что у восстановления; `/VERIFY` сравнивает деревья |

`/JOURNAL=file` - другой журнал.  Без журнала `/SINCE=BACKUP` сохраняет
всё, как в первый раз (VMS так же: нет даты бэкапа - файл не сохранялся).

### 9.3 Безопасность удаления

- `/INCREMENTAL` отказывается работать с saveset-ом без каталога или без
  KIND (X01-01): нельзя удалять по неполному описанию.
- Файл, который по каталогу должен быть (PRESENT), а на диске его нет, -
  предупреждение MISSING: скорее всего пропущен промежуточный saveset.
- `/CONFIRM` спрашивает и перед каждым удалением; `/LOG` сообщает о нём.

### 9.4 Модули

`src/vbkjnl.c` - журнал; `src/vbkcpy.c` - копирование; `vbkrst.c`
отдаёт создание файла как API (`vbk$rst_*`), которым пользуется и
копирование; `vbkwlk.c` сообщает и об отобранных по времени-нет файлах
(флаг PRESENT), когда фильтр по времени задан.


## 10. Этап 3 - конвейер и кэш страниц

**Поток записи** (`lib/vbkwrt.c`).  Основной поток делает всё, что делал:
режет записи на блоки, считает CRC и XOR, решает LASTINVOL, открывает тома
и выдаёт сообщения.  Готовый блок он кладёт в очередь, второй поток только
пишет (`write`) и управляет writeback-ом.  Очередь - не меньше 4 МБ (64
блока по 64 КБ): одно чтение файла (1 МБ) даёт 16 блоков, короткая очередь
вставала бы на каждом.  Перед закрытием тома основной поток ждёт, пока
очередь опустеет, поэтому ошибка записи всегда относится к текущему тому;
она приходит на несколько блоков позже и сообщается так же (WRITERR).
Нет потока (`pthread_create` не смог) или `VBACKUP_PIPELINE=0` - блоки
пишутся сразу; окна writeback-а и подсказки кэшу при этом остаются.
Формат не меняется.

**Writeback окнами по 8 МБ.**  Для каждого окна запись на диск
запускается сразу (`sync_file_range` WRITE), дожидается её следующее окно,
после чего страницы выбрасываются (`POSIX_FADV_DONTNEED`).  Saveset пишется
ровно со скоростью устройства, а не долгим `fsync` в конце (было: 54 с
после последнего файла на 2 ГБ; стало: меньше 0.5 с), и не вытесняет из
кэша рабочие данные.  Каждый том при закрытии - `fsync`.

**Чтение.**  Тома saveset-а и сохраняемые файлы - `POSIX_FADV_SEQUENTIAL`.
Прочитанная группа saveset-а выбрасывается из кэша.  Файл выбрасывается за
чтением, только если он был "холодным": ни одной страницы первого
мегабайта в кэше до чтения (`mincore`).  Файл, который был в кэше, - чьи-то
рабочие данные, его не трогаем.  `vbk$rd_probe` (не saveset ли это?) не
делает холодный файл тёплым.  `vbk$rd_seek` в уже прочитанную группу
берёт её как есть (EXTRACT: следующий файл часто в той же группе).

**Замеры** (44 ядра x86_64, tmpfs -> tmpfs, тёплый кэш): файл 1 ГБ -
1.16 с без потока, 0.79-0.89 с с потоком; 14 тыс. мелких файлов - 0.61 и
0.53-0.58 с.  На диск упираемся в сам диск (на общей машине 55-100 МБ/с,
разброс больше разницы); выигрыш потока там - когда источник и приёмник на
разных устройствах.

**Опережающее чтение файлов** (`src/vbkpre.c`).  Обходчик, прочитав
каталог (`scandir`), отдаёт список его файлов (по `d_type` - обычные или
неизвестные, прошедшие `/SELECT` и `/EXCLUDE`) и забирает его обратно,
когда каталог пройден.  Рабочие потоки (8, `VBACKUP_PREFETCH=n`, 0 - нет)
делают только системные вызовы: `lstat`, `open` (O_NOATIME), чтение
первого 1 МБ в свой буфер, `close`.  Сохранение идёт как прежде, в своём
порядке, и находит страницы в кэше; от опережения в saveset-е не зависит
ничего.  Обход - в глубину, поэтому потоки берут файлы самого нового
каталога: файлы подкаталога идут раньше остатка родителя.  Вперёд - не
больше 128 файлов и 64 МБ; файлы, мимо которых сохранение прошло, место
освобождают.

Холодный ли файл, решает поток до своего чтения: чтение первой страницы с
`RWF_NOWAIT` (EAGAIN - холодный); если на месте и первая, и последняя
страница головы - файл тёплый, и его данные не копируются вовсе.
Сохранение спрашивает вердикт (`vbk$pre_take`); файл, который ни один
поток не начал, у потоков забирается, и сохранение судит о нём само.  При
фильтре по времени большинство файлов - PRESENT, поэтому потоки только
делают `lstat` и ничего не читают.

Замеры (SSD этой машины, данные выброшены из кэша по файлам, inode-ы в
кэше; 21 850 файлов, 540 МБ): сохранение 5.1 с без опережения, 2.45-2.56
с с 8 потоками (2 - 3.0 с, 4 - 2.6 с, 16-32 - 2.6-3.0 с); копирование 8.2
и 4.6 с.  Тёплый кэш (tmpfs): медианы 10 прогонов 1.16-1.18 с в обоих
режимах - без потерь.  NFS и HDD здесь не проверить; там выигрыш должен
быть больше: каждый шаг - ожидание.

**Дальше.**  Поток чтения групп в `vbkrd.c` - позже: восстановление
упирается в создание файлов, а `vbk$rd_seek` пришлось бы отменять
опережение.


## 11. Этап 3 - тест порчи

из трёх способов: FIX - не больше одного блока в группе (всё должно
починиться, BLKLOST нет), LOSE - два и больше блока в части групп, CHAOS -
что угодно: VHDR, TRAILER, обрезанные и пропавшие тома, переставленные и
скопированные блоки.  Восстановление, `/LIST`, `/LIST /FULL` и `/COMPARE`
не должны падать и зависать; главное - никакой тихой порчи: файл, который
восстановлен и не назван в FILDAMAGED, - тот, что сохраняли; файл, который
не восстановлен, назван.  ROUNDS, SEED - повторяемость; в ctest 15 раундов.
Лучше всего гонять на сборке с ASan/UBSan (отчёт санитайзера в логе - тоже
падение).

Тест сразу нашёл дыру: при потере блока с записью FILE файл не
восстанавливался вовсе и не назывался нигде (в раунде LOSE - около 50
файлов из 300).  Теперь восстановление отмечает номера (FILENO) прочитанных
записей FILE в битовой карте и, если блоки терялись, сверяет её с
каталогом: каждый не прочитанный файл - `FILLOST`.  Запись CATALOG цельна
сама по себе, поэтому каталог читается и за дырой.  Нет каталога или он
тоже повреждён - один раз `UNNAMED`: назвать всё нельзя.  Отобранное
`/SELECT`/`/EXCLUDE` и PRESENT не называются.


## 12. Этап 3 - vbkx

`tools/vbkx.c` - извлекатель поверх одного ядра чтения (`libvbkrd`): без
CLI$, HELP и сообщений StarLet (от StarLet - только CRC, и он статический);
собирается статически, если в системе есть статическая libc
(`VBACKUP$M_VBKXSTATIC`), - для машины без VBACKUP.  Команды `l`, `x`, `p`,
`t`; листинг - одна строка на файл (время, размер, тип и права как в ls,
имя), под MultiArc этапа 5.

Без имён saveset читается одним проходом; с именами каждый файл берётся
переходом по каталогу.  Жёсткая ссылка, чьё первое имя не выбрано,
извлекается с данными первого под своим именем.  Восстанавливаются данные,
дыры, права (с битами setuid/setgid/sticky, как у vbackup), времена,
ссылки, FIFO; от root - владелец по номеру и устройства.  ACL, xattr и
флаги chattr - нет (это дело vbackup; на Windows их нет вовсе).  Имена не
доверяются: `..`, ведущий `/`, путь через символьную ссылку отвергаются,
каждый каталог открывается `openat` с O_NOFOLLOW, существующий файл без
`-f` не трогается.  Порча - как у vbackup: неполный файл - "is incomplete",
недостижимый - "was not extracted", без каталога - "cannot all be named".

Проверка: smoke (вывод vbkx совпадает с восстановлением vbackup по типам,
правам, размерам, временам, владельцам и данным; жёсткие ссылки, дыры;
`p`, `t`, извлечение по имени, поддельный saveset, коды завершения),
damage.sh прогоняет vbkx в каждом раунде тем же судьёй.

**Windows (X01-04).**  vbkx.exe собирается MinGW-w64 одной командой
(`make -f tools/Makefile.win`, или `cmake/mingw-w64.cmake`, или цель
`vbkx-exe` обычной сборки, когда есть `x86_64-w64-mingw32-gcc`).  Ядро
чтения - те же `lib/vbkfmt.c`, `vbkrd.c`, `vbklz4.c`: ввод-вывод идёт через
`lib/vbkos.h` (`vbk$os_open`, `_pread`, `_fsize`, `_close`), под `_WIN32`
там же свои STS$K и табличная CRC - StarLet не нужен; `vbk$volspec`
переехал в `vbkfmt.c`, чтобы читатель не тянул writer с его потоком.  В
vbkx системные вызовы создания файлов собраны в слой `s_vbkx$os_*` с двумя
реализациями: Linux - прежние `openat`/O_NOFOLLOW, Windows - пути `\\?\`
в UTF-16 (имена saveset-а - UTF-8), каждый промежуточный каталог
проверяется, reparse point (ссылка, junction) отвергается.  Восстанавливаются
данные и дыры (размер `_chsize_s`), времена (`SetFileTime`), только-чтение
(нет бита записи владельца), каталоги, жёсткие ссылки
(`CreateHardLinkW`); символьные - `CreateSymbolicLinkW` без прав
администратора, если система разрешает, иначе сообщение (wine говорит
«да» и ничего не делает - поэтому созданная ссылка проверяется).  FIFO,
устройства, владельцы - нет, с сообщением.  Имена, которые Windows не
держит (`<>:"\|?*`, управляющие, CON/PRN/AUX/NUL/COM1-9/LPT1-9 в том числе
с расширением, точка или пробел в конце, не UTF-8), не извлекаются, с
сообщением.  Командная строка берётся в UTF-16 и переводится в UTF-8;
stdout - двоичный, листинг побайтно как на Linux.  `test/win.sh` гоняет
vbkx.exe под wine (в ctest - когда есть MinGW и wine): список совпадает
с Linux-vbkx, данные побайтно, порча FIX/LOSE тем же судьёй, поддельный
saveset с `..\` и `c:` в именах ничего не пишет наружу.


## 13. Этап 3 - распаковщики для гиков: vbkx-go, vbkx-rs, vbkx-pl

`tools/go/main.go` и `tools/rust/src/main.rs` - распаковщики "на момент
апокалипсиса": один файл, только стандартная библиотека, собираются одной
строкой (`go build -o vbkx-go main.go`, `rustc -O -C strip=symbols -o vbkx-rs
src/main.rs`) или `make` рядом; CMake их собирает, только если найден
тулчейн (`VBACKUP$M_GEEKS`), и не нужен для них.  Шапка исходника - полное
руководство.

Простота важнее скорости: по блоку за раз, без потоков и mmap.  Команды `l`
(по записям FILE потока, без каталога; время всегда UTC - не нужны файлы
зон), `x` (всё одним проходом), `t`.  Проверка каждого блока, починка
одного плохого в группе по XOR, ресинхронизация после потери, пропуск
пропавшего или обрезанного тома, VHDR тома 1 испорчен - размер блока
подбирается перебором (8192..1 МБ, шаг 512) по CRC следующих блоков,
размер группы - по первому XOR-блоку; том >= 2 без VHDR читается по
следующему блоку.  Неполный файл сохраняется и называется ("is
incomplete"), пропавший - по каталогу, который идёт в конце потока ("was
not extracted"), без каталога - "cannot all be named".  Восстанавливаются
данные, дыры, права (с setuid/setgid/sticky), времена, каталоги, ссылки,
FIFO; владельцы, ACL, xattr, флаги, устройства - нет.  Имена с `..`,
ведущим `/`, пустыми компонентами и путь через символьную ссылку
отвергаются; существующий файл не перезаписывается.  Детерминированы:
одинаковый вход - побайтно одинаковый вывод (map/HashSet только для
поиска, не для порядка).  Rust: ни одного unwrap на данных, единственный
unsafe - utimensat и mkfifo (их нет в std Rust 1.63).

`test/geeks.sh` (в ctest как geeks): список и дерево побайтно как у vbkx
(список - при TZ=UTC), `t`, повторное извлечение, VHDR тома 1 испорчен,
раунды FIX/LOSE/CHAOS тем же судьёй, что damage.sh, два прогона `l`/`x`/`t`
на одном испорченном saveset-е дают одинаковый вывод, поддельный saveset.

`tools/perl/vbkx.pl` (vbkx-pl) - то же на Perl, и собирать нечего: один
текстовый файл, `perl vbkx.pl l|x|t saveset [-C dir]`.  Только то, что есть
в обязательном пакете Debian perl-base (strict, warnings, Fcntl, POSIX;
проверено запуском с @INC только из perl-base), Perl 5.10+, годится и
32-битный Perl: 64-битные поля читаются двумя половинами (точно до 2**53).
CRC-32 - таблицей на чистом Perl; скорость около 2.5 МБ/с на `t` на этой
машине (каждый байт проверяется дважды: блок и файл) - для апокалипсиса
достаточно.  Поведение, сообщения и список - как у vbkx-go/rs, побайтно;
хэши Perl - только для поиска, порядок задают массивы.  Времена - через
системный вызов utimensat (номер для x86_64, aarch64 и ещё нескольких
машин), с наносекундами и для символьной ссылки; на неизвестной машине -
utime() с точностью до секунды, ссылка сохраняет своё время.  Отличия от
go/rs: существующий не-каталог на месте каталога - сообщение (go/rs молча
пропускают).  В geeks.sh - переменная VBKXPL (CMake передаёт её, если найден
perl); предупреждение Perl в логе считается падением.

С X01-04 все три читают DATAZ (`/DATA_FORMAT=COMPRESSED`): свой декодер LZ4
block в каждом языке, с теми же проверками, что `vbk$lz4_decompress` (длины
против остатка входа и rawlen, offset против выведенного, ровно rawlen из
ровно данного входа); плохая запись - файл неполный.  geeks.sh гоняет их на
сжатом saveset-е (то же, что vbkx), на saveset-е из блоков эталонного LZ4
(python3-lz4, режимы default/fast/high) и в раундах порчи - в том числе
ZBODY: мусор внутри сжатых байт с пересчитанным CRC блока, который ловят
только декодер и CRC файла.

С X01-06 все три читают зашифрованные saveset-ы (format.md 6.10): EDATA и
ETRAILER, ключи по PBKDF2-HMAC-SHA256 из SALT/KDFITER VHDR и проверка
KEYCHECK до всего остального (неверная фраза - код 2, ничего не создано);
в группе порядок как в `s_vbk$loadgrp`: CRC и тип, TAG каждого хорошего
блока (CRC верен, TAG нет - сообщение, блок плохой), починка по XOR одного
(восстановленный должен пройти TAG), и только потом расшифровка ChaCha20.
ETRAILER с плохим TAG - сообщение и код 1, поток читается всё равно (geeks
каталогом из TRAILER не пользуются).  Фраза - `-k файл`, иначе
`VBACKUP_KEY_FILE`, иначе терминал без эха через `stty` (в std Go и Rust
нет termios); файл ключа, доступный группе или другим, отвергается.  Том 1
без VHDR - ключи берутся из VHDR другого тома (в каждом одинаковая короткая
SUMMARY); vbkx так не умеет.  Только стандартная библиотека: Go -
crypto/sha256 и crypto/hmac из std, PBKDF2 и ChaCha20 написаны (crypto/pbkdf2
в Go 1.19 нет); Rust - SHA-256, HMAC, PBKDF2, ChaCha20 написаны целиком;
Perl - Digest::SHA, если он есть (его нет в perl-base, грузится только
для зашифрованного saveset-а), иначе свой SHA-256 на чистом Perl
(VBKXPL_PURE=1 включает его принудительно; 600000 итераций PBKDF2 - минуты),
ChaCha20 всегда на чистом Perl (около 2 с на МБ).  Команда `selftest` - векторы из test/units.c (FIPS 180-4,
RFC 4231, RFC 7914, RFC 8439).  geeks.sh: зашифрованный saveset в томах и
сжатый в томах блоками по 16 КБ (VBACKUP_KDFITER=1000) - то же, что vbkx и
что незашифрованный; неверная фраза; файл ключа 0644; поддельный блок
(байт шифротекста, CRC пересчитан) чинится по группе, два в группе -
потеряны и названы; поддельный ETRAILER; раунды порчи и на зашифрованном
(не больше 6).


## 14. Этап 4 - /PHYSICAL

`vbackup /dev/sdb1 sdb1.bck /PHYSICAL` - устройство (или файл-образ)
поблочно.  В saveset-е это один обычный файл (format.md 6.8): данные по
смещениям, куски по 64 КБ из нулей пропущены (дыры), в SUMMARY - PHYSICAL,
DEVSIZE, SECTORSIZE.  Поэтому любой читатель, включая старые vbackup,
vbkx, vbkx-go/rs/pl и vbkx.exe, делает из него разреженный файл-образ;
на устройство пишет только восстановление `/PHYSICAL`.

Защита при сохранении (`src/vbkphy.c`): устройство или его раздел
смонтированы на запись - отказ (PHYSMOUNTED: размонтировать, смонтировать
только на чтение или копировать снимок); занято (holders/: LVM, RAID,
dm-crypt; swap) - отказ (PHYSHELD); открытие с O_EXCL - вторая линия
(кроме смонтированного только на чтение); размер повторно проверяется в
конце (PHYSSIZE для сменного носителя).

Защита при восстановлении: на устройство - только с `/REPLACE`, никогда
на смонтированное, занятое или меньшее (PHYSSMALL); на большее - с
сообщением (файловая система остаётся прежнего размера); за терминалом
нужно набрать YES (y слишком легко); скрипт с `/REPLACE` не спрашивают.
Дыры на устройстве пишутся нулями (BLKZEROOUT, иначе буфер нулей) -
устройство, в отличие от нового файла, хранит старые байты; за пределы
DEVSIZE ничего не пишется.  После - PHYSUUID: у копии те же метки и UUID.

`/PHYSICAL` берёт один вход и не сочетается с `/SELECT`, `/EXCLUDE`,
`/SINCE`, `/BEFORE`, `/BY_OWNER`, `/RECORD`, `/INCREMENTAL` (CONFQUAL).
`/VERIFY` и `/COMPARE` сравнивают данные с устройством.

Проверено: smoke - файл-образ (сжатый и нет, обычное восстановление в
каталог, vbkx), под root - loop-устройства: смонтированное на запись не
берётся, без `/REPLACE` и на меньшее не пишется, восстановление поверх
мусора даёт ровно сохранённое в первых DEVSIZE байтах и не трогает
остальное, на смонтированное не пишется.  Не проверено: holders (нужен
dmsetup), настоящие сменные носители.


## 15. Этап 4 - /IMAGE

`vbackup /mnt/data vol.bck /IMAGE` (или смонтированное устройство) -
все файлы одной файловой системы под собственными именами, без других
ФС внутри неё, без учёта nodump, плюс в SUMMARY то, что делает том
томом: FSTYPE, FSLABEL, FSUUID (udev `/dev/disk/by-*`, для ext* - запас
из суперблока), FSUSED, ROOTATTR (атрибуты корня: владелец, права,
времена, xattr/ACL), MOUNTOPTS (format.md 6.9).  Обычный saveset файлов:
любой читатель восстанавливает его деревом.

`vbackup vol.bck /dev/sdc1 /IMAGE /REPLACE` (`src/vbkimg.c`): защита
`/PHYSICAL` (`/REPLACE`, не смонтировано, не занято, YES за терминалом)
плюс проверка, что файлы поместятся (FSUSED + 5% + 16 МБ); затем
единственный запуск внешней программы - `mkfs.<тип>` по таблице: ext2/3/4
(`-L -U`), xfs (`-L -m uuid=`), btrfs (`-L -U`), vfat (`-n` 11 букв, `-i`
серийный номер); другой тип - IMGUNSUPP, «используйте /PHYSICAL».  Потом
`mount(2)` на `mkdtemp`-каталог с nosuid, nodev, noexec, обычный
`vbk$restore` в него, ROOTATTR на корень последним, `umount2` при любом
исходе.  `/CONFIRM` при восстановлении `/IMAGE` не принимается.

Чем /IMAGE не является: копией загрузочных секторов и таблицы разделов
(это `/PHYSICAL` всего диска) и номеров inode; том, на который пишут, -
согласован пофайлово, не между файлами (снимок).

Проверено (smoke под root, loop-устройства): ext4 с меткой и UUID -
сохранение с точки монтирования, восстановление на другое устройство,
дерево, жёсткие ссылки, корень, метка и UUID совпадают; вручную - vfat
(метка и серийный номер), сохранение по устройству, отказы IMGNOTVOL,
IMGNOTMNT, IMGNOTIMG, IMGSMALL, IMGUNSUPP (minix), PHYSREPLACE,
PHYSMOUNTED.  Не проверено: xfs и btrfs (их mkfs здесь нет).


## 16. Этап 4 - сжатие на нескольких ядрах

Замер на ACS-CGW (Cortex-A35, 4 ядра, 60 МБ в памяти: 45 МБ текста, 15 МБ
случайных): сохранение без сжатия 0.70 с, со сжатием (X01-04, один поток)
2.33 с - сам кодек около 35 МБ/с, медленнее eMMC и USB-диска.

Две меры.  `vbk$lz4_pack` сначала пробует первые 64 КБ куска и при выигрыше
меньше 3% пишет его без сжатия (фото, видео, архивы не стоят времени) -
1.51 с.  `src/vbkzpl.c` - кольцо: записи сохранения идут в него по порядку
(DATA - сжимают рабочие потоки, FILE/FEND - как есть, CALL - запись
каталога, ждущая места своей FILE), пишет основной поток с головы кольца
по порядку, поэтому saveset тот же, что без потоков; CRC файла - в основном
потоке по исходным байтам.  `VBACKUP_ZTHREADS` (по умолчанию ядра, не
больше 8).  4 потока: 0.90 с (около 67 МБ/с против 85 без сжатия).
Восстановление не менялось (0.83 с против 0.58): распаковка LZ4 быстрая.


## 17. Этап 6 - шифрование

Формат - format.md 6.10; здесь - почему так.

**Где.**  Шифруется полезная нагрузка блоков DATA и TRAILER (типы EDATA,
ETRAILER), а заголовки, CRC и XOR-блоки считаются по шифротексту.
Поэтому проверка, починка по группе и ресинхронизация работают без
пароля, а поток записей и весь код над ним не меняются: блок
расшифровывается в ядре чтения, сразу после починки группы.  Новые
типы блоков, а не флаг: читатель до X01-06 считает такой блок плохим
и не разбирает шифротекст как записи (проверено установленным X01-05).

**Чем.**  Два примитива - ChaCha20 (RFC 8439) и SHA-256 (FIPS 180-4), из
второго HMAC и PBKDF2.  Encrypt-then-MAC: TAG на блок (32 байта в
конце нагрузки) покрывает поля заголовка, которые нельзя подменить
незаметно (ssuuid, bsize, blkno, volno, тип, gindex, recoff, paylen), и
шифротекст.  `flags` в TAG не входит: починка восстанавливает его как 0.
Блок с верным CRC и неверным TAG - плохой блок, событие BADTAG
(BLKFORGED), чинится по группе как любой другой.  Poly1305 был бы
быстрее, но ключ PBKDF2 всё равно упирается в SHA-256, а один примитив
хэширования вместо двух проще повторить на Go, Rust и Perl.

**Ключи.**  PBKDF2-HMAC-SHA256, 600000 итераций (OWASP 2023), соль 32
байта на каждый saveset; KENC, KMAC, CHECK - HMAC от MK с метками.
KEYCHECK в VHDR отличает неверный пароль от повреждения.  Nonce -
blkno: уникален внутри saveset-а, ключ уникален на saveset.  Память-
ёмкие KDF (scrypt, Argon2) отвергнуты: на чистом Perl они
неприменимы, а распаковщики для гиков - часть обещания формата.

**Что видно.**  VHDR несёт короткую открытую SUMMARY (продукт,
размеры, параметры KDF) в каждом томе; полная SUMMARY (узел,
пользователь, команда, базы) - первая запись зашифрованного потока.
Видны размеры блоков, групп, томов и длина потока.

**Пароль.**  Никогда из командной строки (CMDLINE хранится в SUMMARY и
виден в ps): /dev/tty без эха, дважды при сохранении; /KEY_FILE или
VBACKUP_KEY_FILE - первая строка файла с правами 600.  Без терминала -
NOKEY, ожидания нет; VBACKUP_NOPROMPT=1 (и `vbkx -n`) для плагинов:
вопрос на экране файлового менеджера повесил бы его.  Пароль один на
команду (после /VERIFY, цепочка /INCREMENTAL) и затирается при выходе.

**Скорость.**  Cortex-A35 (.109, .110): портируемый SHA-256 - 17 МБ/с,
ChaCha20 - 36 МБ/с; зашифрованное сохранение 40 МБ 3,5 с против 0,4 с
без шифрования, PBKDF2 600000 - 5,6 с на каждое открытие.  С
инструкциями SHA-256 ARMv8 (берутся, только если AT_HWCAP их называет
и самопроверка совпала с портируемым кодом; VBACKUP_NOHWCRYPTO=1 -
запрет): HMAC 85 МБ/с, сохранение 1,35 с, открытие 1,6 с.  x86: без
SHA-NI на машинах стенда - портируемый код, 165 МБ/с HMAC, 276 МБ/с
ChaCha20, открытие 0,5 с.  Шифрование при записи идёт в главном потоке
(до XOR); распараллелить его, как сжатие (`vbkzpl.c`), - следующий шаг,
если понадобится.

**Тесты.**  units: векторы FIPS 180-4, RFC 4231, 7914, 8439, подделка
каждого поля TAG, оба пути SHA-256.  smoke: сохранение/листинг/
восстановление/сравнение/тома/сжатие, неверный пароль, нет ключа, файл
ключа с чужими правами.  damage: каждый четвёртый раунд портит
зашифрованный saveset и пересчитывает CRC испорченных блоков - ловит
только TAG.  geeks, wcx, plugins - то же через все читатели.


## 18. Этап 7 - канал и ядра

**Saveset из канала.**  `-` на входе - стандартный ввод.  Ядро чтения
(`vbkrd.c`) читает его один раз и только вперёд: блоки группы по одному,
и хороший TRAILER (ETRAILER) заканчивает группы там, где пришёл - иначе
он попадал бы в последнюю группу и считался потерянным DATA-блоком.
Размера нет (VBK$K_STREAMBLK), томов нет (запись в `-` - один том,
`/VOLUME_SIZE` отвергается), `rd_seek` отказывает, `rd_rewind` - только
внутри первой группы, пока она в руках: так VBK$RD_SETKEY берёт полную
SUMMARY зашифрованного потока и возвращается к началу.  Каталог в конце
потока не помогает, поэтому /EXTRACT ищет файл чтением, а vbkx с именами
отказывает.  NOTRAILER/NOCATALOG в начале канала не пишутся (это не
ошибка), NOTRAILER - если канал кончился без трейлера.

**`lib/` без printf.**  Ядро - это и vbkx, vbkx.exe, WCX: пять `snprintf`
(копии имени, номер тома) заменены прямым кодом; stdio не подключается.
Текст утилиты (`src/`) - только FAO (X01-07).

**Ядра для шифрования.**  Пул `lib/vbkpar.c` (fork-join, только в
vbackup; vbkx и WCX его не видят и считают в одном потоке те же байты)
отдаётся VBKCRP через VBK$CRP_SETPAR.  Запись: ключевой поток ChaCha20
блока полосами (счётчик позволяет считать их независимо), TAG - по-
прежнему последовательно, порядок записи и учёт томов не тронуты.
Чтение: TAG и расшифровка блоков группы параллельно, события - после,
по порядку.  Cortex-A35 (.110), 40 МБ: сохранение 1,35 -> 1,06 с,
восстановление 1,44 -> 0,78 с; x86, 200 МБ: 1,75 -> 1,51 и 1,90 -> 0,67
с.  Дальше сохранение упирается в HMAC блока; распараллелить его можно
только конвейером по группам с отложенной выдачей блоков - тогда учёт
томов (`s_vbk$need`, `volblk`) придётся вести по назначенным блокам.
Кольцо с плотными номерами там лучше skip list-а.


## 19. Этап 8 - тома по сети и конвейер шифрования

**Тома в потоке.**  Писатель кладёт тома в stdout подряд, каждый со своим
VHDR (format.md §2); читатель потока (`vbkrd.c`) принимает VHDR следующего
тома как конец текущего: у тома потока есть `sbase`, байт потока, с
которого он начинается; пропущенные тома - MISSVOL.

**Копия saveset-а (`/TRANSFER`, `vbkxfr.c`).**  Блоки, не записи: пароль
не нужен, копия побайтна; поток раскладывается по файлам томов на каждом
VHDR, тома - склеиваются в поток.  Писатель (`vbkwrt`) не используется:
он переписал бы флаги и CRC и назначил бы свои границы томов.  Плохой
блок не чинится, а копируется как есть (BLKCOPIED): копия хранит то, что
ей дали, чинит восстановление.  Конец без TRAILER - NOTRAILER.

**`node::file` (`vbkrsh.c`).**  VBACKUP на том узле через ssh
(`VBACKUP_RSH`, для тестов - подставной скрипт), saveset - по каналу,
сообщения той стороны - сюда, её код завершения - сюда (REMOTEERR).
Команды той стороны несут `/TRANSFER`: VBACKUP до X01-11 его не знает и
откажет - иначе `vbackup - file` он понял бы как восстановление в
каталог.  `/VERIFY` удалённого saveset-а - чтение его оттуда и сравнение
здесь; целостность (CRC каждого блока, TRAILER) проверяет приёмник.
Доверие - ключи ssh; на том узле нужен X01-11 в PATH неинтерактивного ssh.

**Конвейер шифрования (`vbkwrt.c`, SPIPE).**  Главный поток нумерует блоки
и закрывает тома как прежде (`need`, `volblk`, флаги конца тома не
тронуты), но не шифрует, не считает XOR и CRC; потоки-«печатники»
шифруют EDATA-блоки очереди параллельно (каждый блок целиком: ChaCha20 и
TAG); поток записи берёт блоки по порядку, XOR-ит шифротекст группы,
заполняет XOR-блок, ставит CRC последним.  Без потока записи и на одном
ядре - шифрование на месте.  x86, 200 МБ: 1,74 -> 0,52 с (без шифрования
0,51); Cortex-A35, 40 МБ: 1,43 / 1,21 (X01-10) / 0,70 с.

## 20. Этап 9 - saveset-ы OpenVMS BACKUP

**Что читается.**  Saveset-ы BACKUP на диске (и ленточные, скопированные в
файл с сохранением размера блока): блоки с заголовком BBH 256 байт, записи
с BRH 16 байт - SUMMARY, FILE (атрибуты), VBN (блоки файла по 512 как на
диске).  Формат и всё, что из него следует, - в `doc/vmsbackup.md`;
каждое утверждение там проверено на saveset-ах BACKUP V8.3 с OpenVMS
Alpha V8.3 (ODS-5), положенных в `test/vms` вместе с `MKVBKS.COM`, который
их сделал, листингами `BACKUP/LIST[/FULL]` и FTP-копиями файлов.

**Ядро (`lib/vbkvms.c`).**  Без stdio и без StarLet, как `vbkrd.c`:
его линкуют vbackup, vbkx и vbkx.exe.  Свой цикл по блокам - заголовок в
256 байт и отсутствие каталога не ложатся в `vbkrd.c`.  Чтение строго
последовательное (файл или канал), группами `/GROUP_SIZE` + 1: CRC
(тот же CRC-32/IEEE, что у наших блоков, поля CRC и checksum - нулями),
один плохой блок группы - XOR остальных, включая XOR-блок; заголовок
XOR-блока - тоже XOR, при чётной группе в нём нули вместо struclev и
размера блока, поэтому он судится только по size, applic и CRC.
Плохой первый блок уносит SUMMARY с размером группы: размер берётся по
номеру первого хорошего XOR-блока впереди (упреждающее чтение до 101
блока), и первый блок чинится как любой.  События - через callback
`vbkrd.h` (REPAIRED, LOST, BADREC).

**Распознавание.**  По пяти полям заголовка первого блока (size 256,
struclev 0x0101, applic 1, number 1, размер блока 2048..65535), без CRC:
плохой первый блок - забота ремонта, а не повод счесть saveset файлом и
скопировать.  Наш saveset начинается с "VBKB", BBH - с 256: не спутать.

**Записи в байты Linux.**  Последовательный файл с управлением кареткой -
текст: VAR (счётчик и байт выравнивания прочь, LF), VFC (ещё и
управляющая область), FIX (запись + LF), STM (CR LF -> LF), STMCR (CR ->
LF), STMLF как есть; всё совпало с FTP VMS в режиме ASCII.  Остальное -
как на диске: FIX и UDF без управления кареткой (образы), VAR/VFC без
него (объектники - счётчики сохраняются), индексные и относительные
(VMSRAW: записи без RMS не достать).  Сырые данные пишутся по смещению
VBN, потерянный блок - дыра, а не сдвиг.

**Имена и атрибуты.**  `[A.B]C.TXT;3` -> `A/B/C.TXT`; BACKUP пишет версии
от старшей, поэтому первая версия имени - без версии, следующие - с
";n".  Экранирование ODS-5 снимается, Latin-1 -> UTF-8, `.DIR` -
каталог.  Режим из защиты: R, W; E - x только каталогам (иначе RWED
сделал бы исполняемым каждый текст).  Время - дата ревизии, понятая как
местное время (VMS часового пояса не хранит).  UIC не владелец Linux:
владелец - тот, кто восстанавливает.  `/COMPARE`, `/INCREMENTAL`,
`/ORIGINAL`, `/IMAGE`, `/TRANSFER` к такому saveset-у - QUALUSE.

**Листинг.**  `/LIST` и `/LIST/FULL` печатают то же, что BACKUP V8.3,
байт в байт (`test/vms.sh` сравнивает с его листингами); UIC - в
восьмеричной, как у BACKUP.

**Попутно.**  `/LIST/FULL` слитно (квалификаторы, приклеенные друг к
другу и ни к чему) в X01-12 резался на параметр "/LIST" и `/FULL`, и
saveset восстанавливался в каталог `/LIST`; теперь такое слово - только
квалификаторы (`s_vbk$glued`), в smoke - проверка.

## 21. Этап 10 - Reed-Solomon: несколько плохих блоков группы

**Зачем.**  XOR-блок чинит один блок группы; носители же портятся
пачками - соседние сектора, царапина, кусок ленты.  `/PARITY=m` закрывает
группу m блоками чётности, и любые m плохих блоков группы (данные или
чётность, подряд тоже) восстанавливаются.

**Совместимость.**  Без `/PARITY` (и с `/PARITY=1`) saveset - версии 1,
байт в байт прежний: строка 0 - это и есть XOR-блок.  С m >= 2 в каждом
заголовке версия 2: читатели до X01-14 (группы у них позиционные, N + 1
блоков) отказывают на первом блоке (NOTSAVESET), а не путают группы
молча.  Тег PARITY (93) - в SUMMARY и в открытой части VHDR
зашифрованного saveset-а.

**Матрица.**  GF(2^8), полином 0x11D; a(j, i) = y_i / (j + y_i), y_i =
128 + i - матрица Коши 1 / (x_j + y_i), x_j = j, со столбцами,
нормированными так, что строка 0 - единицы (XOR).  Любая квадратная
подматрица Коши невырождена, нормировка это сохраняет: любые n из n + m
блоков дают группу.  Вандермонд α^(i·j) отвергнут: при выживших строках
не подряд (XOR потерян, живы 2 и 3) его подматрицы в GF(256) бывают
вырожденными.  `test/units.c` проверяет все наборы потерь до m = 4 при
n <= 10.

**Заголовки.**  XOR покрывает только payload: `recoff`/`paylen`
потерянного блока брались из `prv*` следующего - при двух потерях подряд
первый блок бесполезен.  В версии 2 те же строки применяются к 8 байтам
`recoff‖paylen` каждого блока данных, и строка j лежит в полях
`recoff`/`paylen` блока чётности j.  `gindex` блока чётности - n + 256·j:
любой хороший блок чётности называет и n, и свою строку.

**Ремонт (`vbkrd.c`, `s_vbk$loadgrp2`).**  e потерь, e хороших строк:
синдромы, Гаусс-Жордан e×e один раз на группу, применение по байтам;
сначала 8 байт заголовков, потом payload.  Лишние хорошие строки
пересчитываются и сверяются: расхождение значит блок с верным CRC и
неверными байтами.  Тогда попытка повторяется без каждой хорошей строки
по очереди - одна подделанная строка обходится, пока строк хватает; если
не сходится никак - PARITYERR, группа не восстанавливается.  У
зашифрованного saveset-а восстановленный блок ещё и проходит TAG.

**Писатель (`vbkwrt.c`).**  m аккумуляторов: строка 0 - прежний XOR по
квадрословам, строки >= 1 - умножение-сложение по таблице произведений
коэффициента; чётность заголовков - в главном потоке, чётность payload в
конвейере шифрования (SPIPE) - в потоке записи по шифротексту, в порядке
блоков, как XOR.  Минимальный том - (N + m + 2) блоков.

**Цена.**  300 МБ, блок 64K, группа 10, x86: сохранение 0,74 / 0,84 /
0,88 / 1,01 с при m = 1 / 2 / 3 / 4; saveset больше на m/N.  Чтение
неповреждённого saveset-а не дороже: строки пересчитываются только при
починке.

**Читатели.**  vbkx, vbkx.exe, модуль WCX - через `vbkrd.c` и
`vbkrs.c`; vbkx-go, vbkx-rs, vbkx-pl - своя реализация того же (таблицы,
обращение, повтор без строки), каждый со своей самопроверкой.

## 22. Этап 11 - SIMD для Reed-Solomon

**Умножение.**  dst ^= c·src в GF(2^8) по полубайтам: LO[x] = c·x, HI[x] =
c·(x << 4) для x < 16, байт b - LO[b & 15] ^ HI[b >> 4]; обе таблицы по 16
байт ложатся в регистр, поиск - одна инструкция перестановки на 16/32
байта: `pshufb` (SSSE3), `vpshufb` (AVX2), `vqtbl1q_u8` (NEON).  Хвост
короче вектора - те же таблицы побайтно.

**Выбор.**  При первом вызове `vbk$rs_init`: на x86 по
`__builtin_cpu_supports` (AVX2, иначе SSSE3; функции собраны с атрибутом
`target`, остальной код - для базового x86-64), на aarch64 NEON есть
всегда.  Выбранное сверяется с переносимым кодом на 37 коэффициентах; не
сошлось или `VBACKUP_NOSIMD=1` - переносимый код.  `vbk$rs_simd()`
называет выбранное; `test/units.c` сверяет оба пути на длинах и
смещениях, CTest гоняет его как есть.

**Цифры.**  muladd 64K: x86 (AVX2) 18,0 ГБ/с против 1,37; Cortex-A35
(NEON) 675 МБ/с против 89.  Сохранение 300 МБ: m = 8 - 1,20 с против
1,99, m = 4 - 0,92 против 1,11; остаток над m = 1 (0,78 с) - запись
большего объёма, не вычисление.

## 23. Этап 12 - поток чтения групп (измерен, не сделан) и скорость распаковщиков

**Поток чтения групп** был отложен с этапа 3; перед тем как его писать,
измерено, есть ли что выигрывать.  x86, ext4 на SSD, 1,1 ГБ: восстановление
с холодного диска 2,30 с, одно чтение того же saveset-а (dd) 2,19 с -
восстановление уже упирается в чтение: ядро читает вперёд само
(последовательный pread), запись файлов уходит в кэш и пишется отложенно.
Поток мог бы снять не больше 5%.  Cortex-A35 (.110), eMMC, 200 МБ:
восстановление 27,4 с = чтение 12,8 + запись 16,0 - один носитель и читает,
и пишет; из кэша (saveset уже прочитан) то же 27,6 с.  Перекрытие
невозможно, поток ничего не даст.  Решение: не делать; вернуться, если
появится случай saveset и файлы на разных медленных носителях, где
измерение покажет сумму вместо максимума.

**Распаковщики для гиков.**  100 МБ, `/PARITY=3`, 482 плохих блока из 2087:

| | до: чистый / с ремонтом | после |
|---|---|---|
| vbkx-go | 0,16 / 1,06 с | 0,14 / 0,36 с: XOR по 8 байт, цикл таблицы без проверок границ (векторных инструкций в одном файле Go нет) |
| vbkx-rs | 0,70 / 0,89 с | 0,21 / 0,27 с: AVX2/SSSE3/NEON через `std::arch` со сверкой при запуске, `VBACKUP_NOSIMD`; CRC slicing-by-8 |
| vbkx-pl | 45,6 / 47,2 с | 0,26 / 0,52 с: CRC через `Compress::Raw::Zlib` (ядро perl с 5.10), когда он есть; `VBKXPL_PURE=1` - свой код |

**Попутно.**  `vbackup x.bck /work/restore/full`: слово резалось на
`/work/restore` и `/FULL`, если `full` ещё не было (а `.../r` давало
"Ambiguous qualifier") - с X01-06, когда появились приклеенные
квалификаторы.  Теперь часть перед квалификаторами - существующий каталог
- значит, слово целиком имя в нём; проверка в smoke.


## 24. Этап 13 - vbackup.exe, утилита в Windows (фаза 1)

**Путь.**  Родная сборка MinGW-w64, не Cygwin: образ статический, без
DLL среды, понятный пользователю Windows.  Кросс-сборка в Linux
(`cmake/mingw-w64.cmake`); сборка для Linux делает её сама как
ExternalProject, когда есть MinGW-w64 и комплект StarLet рядом с деревом.

**Слой ОС под POSIX-именами, а не вызовы vbk$os_\*.**  `win/vbkwin.h`
подставляется в каждый исходник компилятором (`-include`) раньше его
собственных заголовков: сначала берутся заголовки MinGW, потом их имена
переопределяются макросами (`open`, `stat`, `lstat`, `statx`, `opendir`,
`scandir`, `fopen`, `tmpfile`, `rename`, `getenv`, ...) на подпрограммы
`src/vbkosw.c`.  Модули Linux не переписывались - правки в них точечные
(`vbackup.c`, `vbkmsg.c`, `vbkrst.c`, `vbkkey.c`, `vbkrsh.c`, `vbkjnl.c`,
`vbklst.c`, `lib/vbkos.h`, `include/vbkdef.h`).  Опасность такого пути -
пропущенный вызов, который молча уходит в ANSI-функцию C-библиотеки
(кодовая страница, текстовый режим, 32-битный размер).  Пропустить вызов
под переопределённым именем нельзя - это макрос на всю единицу
трансляции; от имён, которые не переопределены, защищает проверка
импорта в `test/winutil.sh`: в объектах vbackup.exe не должно быть
`open`, `_stat64`, `fopen`, `tmpfile`, `rename`, `getenv` и подобных.

**Что даёт слой.**  Имя UTF-8 -> UTF-16, полный путь, префикс `\\?\` для
длинных.  Файл открывается CreateFileW и получает дескриптор C-библиотеки
через `_open_osfhandle`, всегда в двоичном режиме; read/write/close - её.
Каталог открывается так же (FILE_FLAG_BACKUP_SEMANTICS), а `openat`,
`fstatat`, `unlinkat`, `fdopendir` находят его путь через
GetFinalPathNameByHandleW - так код восстановления, построенный на
дескрипторах каталогов, работает без изменений.  `stat`: том (серийный
номер) и идентификатор файла NTFS вместо dev/ino - жёсткие ссылки
находятся как в Linux; четыре времени в наносекундах, время создания -
BTIME.  Символьные ссылки и junction-ы - S_IFLNK, `readlink` читает
reparse-данные, O_NOFOLLOW их отвергает (ELOOP); прочие reparse-точки
(дедупликация, облачные файлы) открываются как то, что в них.  Режим
выдуман: 0755 каталог, 0644/0444 файл по атрибуту "только чтение";
`chmod` ставит только его.  Владельца нет (0), `chown` ничего не делает.
`pread/pwrite` - OVERLAPPED; `flock` - LockFileEx; `tmpfile` - в TEMP
пользователя (у MSVCRT - в корне диска, куда пользователь писать не
может); `getenv` - из широкого окружения в UTF-8, HOME по умолчанию -
профиль пользователя.  Консоль: `CONIN$` открывается без флагов файла,
кодовая страница вывода - UTF-8 на время работы образа; стек 8 МБ, как в
Linux (пути UTF-16 лежат на стеке).  `pread/pwrite` через OVERLAPPED
двигают указатель файла - дескриптор читается/пишется либо по смещению,
либо подряд, не вперемешку (так у всех вызывающих).

**StarLet - из комплекта, без правок.**  Установленный StarLet - Linux-
библиотека; для Windows три его модуля компилируются из
`../starlet-x.y.z` с `win/vbkwcrt.h` впереди (TIME_UTC и timespec_get для
MSVCRT, O_CLOEXEC, NAME_MAX, S___TIME), заголовки `Windows.h` и
`arpa/inet.h` подменяются из `win/inc`.  Для StarLet найдено и
отложено к исправлению у него самого: эти пять пробелов и
`__declspec(thread)` в `utility_routines.c`, который GCC игнорирует - кэш
префикса сообщений там общий для потоков.  Без NDEBUG StarLet приписывает
к сообщениям `[модуль\функция:строка]` - сборка для Windows задаёт NDEBUG,
как и Linux.

**Имена.**  `vbk$mkpath` в Windows отвергает то, что Windows понимает
иначе: `:` (поток другого файла), `<>"|?*\`, управляющие символы, точку

OPENOUT с причиной "not a valid name on Windows", как у vbkx.exe.  Два

записано в другом регистре (VBK$W_SAMECASE).  `vbk$isabs`: BASE saveset-а,
сделанного в Windows, - "C:/dir"; `/ORIGINAL` и журнал его принимают.

**Отвергнуто в фазе 1.**  `/PHYSICAL`, `/IMAGE` (сразу, QUALUSE "not on
Windows"), `node::file` (REMOTE: нужен ssh.exe Windows - фаза 2),
упреждающее чтение (`vbkpre.c` построен на preadv2(RWF_NOWAIT) - заглушки

## 25. Этап 14 - vbackup.exe, фаза 2

**Формат.**  Два тега FILE в пустом промежутке 21..31: WINATTR (u32,
FILE_ATTRIBUTE_* - только то, что говорит, что такое файл: только
чтение, скрытый, системный, архивный, временный, не индексировать; не
каталог, не reparse, не sparse, не сжатый - это то, как он лежит) и NTSD
(self-relative дескриптор, как его даёт GetKernelObjectSecurity).
WINATTR кладётся и в CATALOG - 4 байта, чтобы `/LIST /FULL` показывал
"Windows: HIDDEN ARCHIVE"; NTSD - нет: дескрипторы по сотне байт и
больше раздули бы каталог.  Версия формата не меняется: читатель X01-17 и
все распаковщики (vbkx, vbkx-go/rs/pl) теги пропускают - проверено.
format.md 6.1, 6.4, 6.11.

**Потоки NTFS - XATTR `user.<поток>`.**  Так их показывает ntfs-3g
(streams_interface=xattr), значит обмен симметричен: поток из Windows
восстанавливается в Linux атрибутом `user.`, атрибут `user.` из Linux -
потоком в Windows.  Прочие пространства имён Linux (`security.`,
`trusted.`, `system.`) в Windows некуда деть - при восстановлении они
молча пропускаются, поэтому `/XATTRS` снова по умолчанию включён.
Предел 64 КБ на значение - предел Linux; поток длиннее не сохраняется, и
об этом теперь говорит XATTRSKIP.  Это касается и Linux: раньше
нечитаемый расширенный атрибут пропускался молча, теперь сохранение
кончается предупреждением (код 1).  Список - FileStreamInfo по
дескриптору; значение - CreateFileW("файл:поток").  Файл "только чтение"
на время записи потока делается записываемым.

**Дескриптор и владелец.**  vbk$w_init включает SeBackupPrivilege,
SeRestorePrivilege, SeSecurityPrivilege, SeCreateSymbolicLinkPrivilege,
если они есть у учётной записи (повышенный администратор).  Есть
привилегия восстановления - это root Linux: `/OWNER=ORIGINAL` по
умолчанию, дескриптор возвращается целиком (владелец, группа, DACL,
SACL при привилегии безопасности) через SetSecurityInfo с PROTECTED или
UNPROTECTED по флагу SE_DACL_PROTECTED - наследуемое от нового родителя
пересчитывается.  Нет - `/OWNER=DEFAULT` и дескриптор не трогается вовсе:
DACL с другой машины может оставить пользователя без доступа к
собственным восстановленным файлам; файл получает ACL каталога, как
файл, созданный руками.  Дескриптор из saveset-а - недоверенные байты:
IsValidSecurityDescriptor сам идёт по смещениям внутри, не зная конца
буфера, поэтому сначала своя проверка (`s_vbk$sdcheck`: заголовок, каждый
SID и ACL целиком внутри элемента), затем RtlValidRelativeSecurityDescriptor
с длиной (под wine она пропускает смещение за край - проверено тестом);
поддельный - ATTRERR "not valid".  Неудачный поиск SID тоже кэшируется:
SID удалённой учётной записи иначе спрашивался бы у контроллера домена
для каждого файла.  UNAME/GNAME - имена SID владельца и группы
(`ДОМЕН\имя`, кэш на 16 SID: LookupAccountSidW может ходить к
контроллеру домена).  `/OWNER=`*имя* и `/BY_OWNER` в Windows
отвергаются (QUALUSE): uid_t не вмещает SID.

**Разреженные файлы.**  SEEK_DATA/SEEK_HOLE - по
FSCTL_QUERY_ALLOCATED_RANGES, только у файла с FILE_ATTRIBUTE_SPARSE_FILE;
не разреженный - EINVAL, вызывающий читает его целиком, как на ФС Linux
без такого вопроса.  Дыры при восстановлении: pwrite за концом файла или
ftruncate дальше конца сначала делают файл разреженным
(FSCTL_SET_SPARSE), а ftruncate идёт через FileEndOfFileInfo - `_chsize`
C-библиотеки дописывает нули.  Так поведение Linux воспроизведено без
изменений в vbkrst.

**node::file через ssh.exe.**  CreateProcessW с наследуемыми копиями
концов `_pipe` и стандартных дескрипторов, затем `_dup2` своего конца на
0 или 1 - как fork/dup2 в Linux.  Командная строка Windows квотируется по
правилам CommandLineToArgvW, команда удалённой стороны - по-прежнему в
одинарных кавычках оболочки.  Процессы - таблица {pid, HANDLE} на 4
места (вход, выход, проверка).  Для теста - `test/fakessh.c`: запускает
команду локально, подменяя `vbackup` на FAKESSH_VBACKUP.

**Проверка.**  `test/winutil.sh` (72 проверки): атрибут HIDDEN под wine
сохраняется, виден в листинге Linux и возвращается, у простого файла не
появляется; имена владельцев из дескриптора; восстановление с
`/OWNER=ORIGINAL` без ошибок; сохранение в `node::file` и
восстановление оттуда через fakessh.exe; поддельные дескрипторы (короче
заголовка, смещение за край) отвергаются, файлы восстанавливаются.  Под
wine не проверить:
потоки (wine их не хранит), реальные дыры (FSCTL_SET_SPARSE там ничего
не делает), применение чужого владельца и SACL - это для настоящей
Windows.

**Дальше (не сделано).**  VSS (теневые копии - читать занятые файлы);
потоки длиннее 64 КБ (свой тег вместо XATTR); `/OWNER=`*имя* через
LookupAccountNameW; восстановление WINATTR и потоков в vbkx.exe; CI на
настоящей Windows (GitHub Actions + MSYS2).


## 26. Этап 15 - сжатие сильнее: Deflate и LZMA

**Требование пользователя:** за всеми компрессорами не должна пострадать
возможность восстановить всё в день X.  Оно определило устройство:

1. **Самопроверка записи.**  `vbk$data_pack` после сжатия каждой записи
   распаковывает её в буфер и сравнивает с исходными байтами; запись,
   не вернувшаяся такой же, пишется как DATA, и об этом говорит ZCHECK.
   Ошибка кодировщика не может испортить saveset - только сделать его
   больше.  Касается и LZ4 - это меняет всех, кто уже сжимает: LZ4 на
   одном ядре 203 -> 133 МБ/с (текст), 232 -> 155 МБ/с (бинарные);
   пул потоков перекрывает это с запасом.  Буфер проверки - у каждого
   слота пула, выделяется вместе со слотом: без памяти пул не стартует
   (сжатие идёт в основном потоке, тоже с проверкой), молча без
   проверки не работает.
2. **Независимость записей.**  Каждая DATAZ сжимается отдельно (запись
   <= 1 МБ, своё окно/словарь) - порча стоит одной записи; ремонт по XOR и
   чётности работает ниже, на блоках, и от кодека не зависит.
3. **Строгие распаковщики.**  Каждый код, длина, расстояние проверены;
   ровно `rawlen` байт; Deflate кончается в последнем байте записи,
   LZMA - маркером конца, код range-декодера 0, вход исчерпан.  Ни один
   из кодеков не имеет своей контрольной суммы - испорченный поток может
   дать другие байты; это ловят CRC блока (порча носителя) и CRC файла в
   FEND (подделка с пересчитанным CRC блока) - файл называется
   повреждённым, никогда не выдаётся молча неверным.  Проверено: smoke
   (поддельные блоки сжатых данных, vbackup и vbkx), geeks (ZBODY - мусор
   внутри сжатых байтов с пересчитанным CRC, на кодеках 2 и 3, для Go,
   Rust, Perl), damage (300 раундов, LZ4/Deflate/LZMA вперемешку).
4. **Четыре независимых декодера** - ядро (C), Go (Deflate из stdlib,
   LZMA свой), Rust (оба свои), Perl (Deflate через Compress::Raw::Zlib
   или свой чистый, LZMA свой) - и сторонние: python zlib и lzma читают
   записи VBACKUP, распаковщики VBACKUP читают потоки zlib (все уровни и
   стратегии, окна 9 и 15 бит - 280 потоков) и liblzma (быстрый,
   нормальный, экстремальный - 70 потоков).  `format.md` 6.7.2, 6.7.3
   достаточно для пятого.
5. **Старые читатели** (X01-18 и раньше) на кодеке 2/3 говорят BADREC и
   FILDAMAGED - проверено на установленном X01-18 и на vbkx-go, vbkx-rs,
   vbkx-pl из main (X01-18): код 1, файлы названы, ни одного молча
   неверного, ни одной паники.

**Выбор кодеков.**  Замер на этой машине (tar исходников vBACKUP 2,7 МБ /
бинарников 2,3 МБ): LZ4 2,46x/1,48x, gzip -6 3,69x/1,91x, xz -6
5,43x/2,56x.  Пользователь выбрал оба: Deflate (простые распаковщики, Go

## 27. Этап 16 - LZMA посильнее: оптимальный разбор

**Формат и распаковщики не меняются** - меняется только выбор
кодировщика: поток тот же LZMA1, его читают ядро, vbkx-go/rs/pl, python.

заголовках: смещение массива `prev` осталось от фиксированного размера -
запись за край на маленьких записях (units на синтетике не ловил: собран
без санитайзера) - исправлено; отсюда и `test/memcheck.sh`.

**Пул сжатия.**  Мелкий файл занимает 3..4 слота кольца (FILE, данные,
FEND, вызов каталога); при 2n+2 слотах одновременно сжималось 4..5
записей - на быстрых уровнях незаметно, на медленных - потолок.  Теперь
16n слотов (не больше 128), буферы слотов по размеру записи, а байты
данных в кольце ограничены тем же бюджетом 2n+2 МБ - память та же.
`/usr/include` (210 МБ, 8 потоков): /LEVEL=2 2,3 -> 1,5 с, 5: 5,1 -> 2,7,
8: 37 -> 15,7, 9: 49 -> 24,5.

**Честно о мелких файлах.**  Каждый файл сжимается отдельно - на
`/usr/include` /LEVEL=9 даёт 53 МБ, а `tar | xz -6` - 19 МБ: общее у
соседних файлов не используется.  Это цена независимости записей (плохой
блок - один файл).  Направление на будущее - "твёрдые" записи из
нескольких мелких файлов (ограниченных, скажем, 1 МБ): плохой блок
стоил бы группы файлов, сжатие приблизилось бы к tar.

**valgrind.**  `test/memcheck.sh` - units, сохранение и восстановление
на уровнях 1, 2, 5, 6, 8, 9 и с /ENCRYPT /PARITY под memcheck (ошибки и
"definitely lost"; потоки пулов - "possibly lost" - не считаются).  Около
двух минут на ПК, на ARM в разы дольше, поэтому по умолчанию выключен:
`-DVBACKUP$M_MEMCHECK=ON`.  perf - инструмент разработки, им найдены все
три горячих места этого этапа.


## 28. Этап 17 - твёрдые записи (SOLID)

**Зачем.**  Раздел 27 кончился честным счётом: `/usr/include` /LEVEL=9 -
53 МБ против 19 МБ у `tar | xz`.  Две причины: каждая запись DATAZ
начинает с пустого словаря, а записи FILE и FEND (и каталог) не сжаты
вовсе - на дереве исходников это около 11 МБ из 53.  Модель на
`/usr/include` (LZMA6): по файлу 34,8 МБ данных, группами по 64 КБ -
22,9, по 256 КБ - 21,8.

**Формат (format.md 6.12).**  Запись SOLID, тип 8: u32 кодек (как у
DATAZ), u32 rawlen (до 1 114 112), u32 count (справочно), сжатые байты.
Внутри - полные записи FILE, DATA, FEND подряд, каждая целиком, ничего
другого.  Сохранение, где SOLID может быть, - версия 3 в каждом блоке;
раскладка групп та же, что у версии 1 или 2 (по тегу PARITY).  Старые
читатели (до X01-21) отказывают на первом блоке (NOTSAVESET), а не
считают файлы группы пропавшими.  Тег каталога 23 SOLID: LOC участника -
это SOLID, читатель по каталогу распаковывает его и проходит соседей
до своего FILENO.

**Писатель (`src/vbksav.c`).**  Обычный файл до 256 КБ (FILE до 32 КБ)
при сжатии - участник: его записи идут в буфер группы, запись каталога
ждёт.  Всё прочее (каталог, ссылка, большой файл, PRESENT) сначала
закрывает группу - порядок потока и каталога = порядок обхода, и
восстановление по потоку делает каталоги раньше их файлов, как раньше.
Группа закрывается до 1 МБ и в конце обхода.  Сжимает её пул
(`vbk$zp_solid`, слот VBK$K_ZK_SOLID), пишет в свою очередь
`s_vbk$gwrite`: SOLID и LOC всех участников - его место; или, если
ZCHECK или не сжалось, записи как есть, LOC - их FILE.  Один поток - то
же синхронно, байт в байт.

**Читатель (`lib/vbkrd.c`).**  `vbk$rd_next` в версии 3 открывает SOLID
и отдаёт его записи по одной, как будто они в потоке; `insolid` говорит,
что запись из SOLID (поиск по каталогу проходит соседей).  Не
открылся (кодек, длины, поток, тип или длина внутренней записи) -
BADREC и пропуск, как потеря блоков: участники не видны и называются
FILLOST по каталогу.  `rd_seek` и `rd_rewind` бросают открытый SOLID.

**Размер группы.**  Измерено (байты сохранения, с каталогом и XOR):

| Дерево, уровень | 64 КБ | 256 КБ | 1 МБ | без SOLID |
|---|---|---|---|---|
| `/usr/include` L1 | 64,7 | 62,4 | 61,9 | 81,0 |
| `/usr/include` L6 | 39,7 | 36,8 | 35,8 | 55,6 |
| `/usr/include` L9 | 36,8 | 33,2 | 32,0 | 53,0 |
| `/usr/lib/python3` L6 | 158,9 | 151,7 | 146,4 | 172,1 |
| `/usr/lib/python3` L9 | 149,4 | 141,0 | 134,6 | 163,1 |

Выбран 1 МБ (`VBK$K_SOLIDGRP`): на 4-5 % лучше 256 КБ.

**Цена в день X.**  При обычной чётности (XOR) один плохой блок группы
чинится, как и прежде - damage.sh с SOLID зелёный (3 x 60 раундов FIX,
LOSE, CHAOS без тихой порчи).  Но потеря сверх чётности стоит теперь
всего SOLID, а не одного файла: в smoke один неисправимый блок унёс 50
мелких файлов из 60 (все названы FILLOST).  Отсюда совет в руководствах:
сохранениям, которые должны пережить тяжёлую порчу, - `/PARITY=2` и
больше, или `/NOSOLID`.

**Тесты.**  units 34 (поддельные SOLID: кодек, rawlen, обрезанный поток,
DATAZ внутри, длина за край, версия 1, поиск бросает SOLID); smoke 18
(версии, дерево, /EXTRACT и /SELECT участника, vbkx p, потеря SOLID);
damage.sh - Deflate и LZMA с SOLID, LZ4 с /NOSOLID; memcheck - мелкие
файлы, /NOSOLID, /EXTRACT участника; geeks - три вилки.

**Попутно.**  vbkx-go на незнакомой версии не отказывал, а перебирал
~2000 размеров блока, читая каждый раз целый блок (минуты на сохранение) -
теперь отказ сразу, а перебор читает сначала заголовок.  Ключ в
winutil.sh и memcheck.sh - строка base64: случайные байты иногда
начинались с перевода строки (пустая первая строка - отказ KEYFILE).


## 29. Этап 18 - надёжность после SOLID

**Ничего не пропадает молча.**  До X01-22 восстановление сверяло каталог
с прочитанными записями FILE только после потери блоков.  Запись, которую
читатель не знает (SOLID в сохранении версии 1, подделка), пропускалась
по длине - и её файлы исчезали без слова; `/COMPARE` и `/VERIFY` молчали
и о файлах, потерянных в плохих блоках ("Differences: 0").  Теперь сверка
всегда: восстановление (`s_vbk$lostcat`), vbkx (`s_vbkx$lostcat`),
сравнение (`s_vbk$catcmp`); поток (канал) - по записям CATALOG, как они
идут.  Потеря блоков - FILLOST, иначе новое NOTINSTREAM; в сравнении -
COMPARERR и различие.  vbkx-go, -rs, -pl так уже делали.

**Сколько стоит битая группа.**  Опыт: python3/dist-packages (23 тыс.
файлов), в случайной группе портятся 2 блока (больше, чем чинит XOR),
40 раз, считаются FILLOST/FILDAMAGED/NOTINSTREAM:

| Вариант | L6, файлов | L6, размер | L1, файлов | L1, размер |
|---|---|---|---|---|
| без SOLID | 19,4 | 171,6 МБ | 10,6 | 268,6 МБ |
| SOLID 1 МБ (X01-21) | 52,3 | 146,2 МБ | 45,3 | 253,6 МБ |
| 1 МБ + спасение | 39,5 | 146,2 МБ | 30,9 | 253,6 МБ |
| **256 КБ + спасение** | **23,9** | **151,4 МБ** | **21,5** | **254,3 МБ** |
| 128 КБ + спасение | 27,1 | 154,9 МБ | 25,9 | 255,3 МБ |

Выравнивание SOLID по группам чётности не сделано: короткая группа внутри
тома нарушает правило 3 раздела 7 (поиск читателей X01-21 считает группы
равными), а набивка до границы стоит ~10 %.

**Спасение оборванной SOLID** (`s_vbk$solcut`).  Тело SOLID, оборванное
потерей блоков или концом потока, распаковывается, насколько оно верно:
`vbk$lz4_decode`, `vbk$dfl_decode`, `vbk$lzm_decode` отдают `a_got` -
сколько байт выхода получено из входа как он есть.  LZ4 и Deflate не
пишут ничего, не проверив (Deflate берёт короткий код из таблицы, только
если его биты есть, длинный - по биту с отказом на конце; коды блока при
отказе сохраняют позицию); LZMA при нехватке входа подставляет нули,
поэтому верно всё до начала символа, на котором вход кончился
(`l_good`).  Записи, целиком лежащие в этом, отдаются, затем разрыв;
файл на разрыве - неполный (нет FEND), прежние проверены своим CRC.
Тест 35: 873 обреза на всех уровнях - ни одного неверного байта.
Работает и для сохранений X01-21.

**Группа 256 КБ** (`VBK$K_SOLIDGRP`): размер +3,5 % к 1 МБ, а потери на
битую группу вчетверо меньше, всего на четверть больше, чем без SOLID.
`/usr/include` /LEVEL=9 - 33 МБ (X01-21: 32, без SOLID: 53).

**Хвост блока за PAYLEN** (найдено damage.sh, сид 7).  Чётность считается
по всей области данных блока, а TAG покрывает только PAYLEN октетов
шифротекста; хвост за ним писатель оставляет нулевым, но ничто его не
подписывает.  Байт, изменённый там в "хорошем" блоке (CRC переподписан),
ломал ремонт соседнего плохого блока группы: в /ENCRYPT - PARITYERR и
ничего не восстановлено, в открытом сохранении - блок "восстановлен"
неверно, ловил только CRC файла.  Теперь перед ремонтом хвосты хороших
блоков данных обнуляются (`s_vbk$canon`), в vbkx-go, -rs, -pl - то же.
Ошибка с X01-06 (/ENCRYPT) и X01-14 (/PARITY); smoke 19 её воспроизводит.

**Испорченный ETRAILER** (damage.sh, сид 8, тихая порча).  `vbk$rd_setkey`
при верном пароле и ETRAILER с неверным TAG отдаёт STS$K_WARN (читать без
каталога); `vbk$key_unlock` возвращал его как есть, а все вызывающие
проверяют младший бит - восстановление, листинг, сравнение выходили, не
прочитав ни записи и не сказав ни слова ("Files: 0").  Зашифрованное
сохранение с повреждённым последним блоком не восстанавливалось вовсе -
с X01-06.  Теперь - BLKFORGED, NOTRAILER и чтение всего потока, как в
vbkx; smoke 19 воспроизводит.

**Тесты.**  units 35 (обрезы потоков, SOLID с обрывом); smoke 19
(сохранение версии 1 с SOLID: NOTINSTREAM, COMPARERR, vbkx; файлы до
обрыва возвращаются); damage.sh 3 x 60 раундов без тихой порчи.


## 30. Этап 19 - восстановление на всех ядрах

**Где время.**  Восстановление /usr/lib/python3 /LEVEL=6, 9 - 11..12 с при
3 с на /LEVEL=1: распаковка LZMA (~50 МБ/с на ядро) в одном потоке.

**Как.**  `vbk$rd_next` разделён на два слоя: `s_vbk$raw` читает запись
как она лежит (SOLID не раскрыта; оборванная SOLID - с числом байт), над
ним - раскрытие SOLID.  Пакетный режим (`vbk$rd_batch`, включают
восстановление и сравнение после ключа): записи читаются вперёд - до 4 на
поток (не больше 64) и 64 МБ, - DATAZ и SOLID среди них распаковываются
разом через пул утилиты (`vbk$crp_par`, тот же, что у шифрования,
`VBACKUP_CTHREADS`), затем отдаются по порядку; DATAZ - сразу как DATA,
которую она заменяет (при неудаче - как есть: вызывающий сообщит, как
прежде).  Никаких потоков в библиотеке: вызов пула синхронный, порядок
записей, флаги resync и insolid - те же, что по одной (тест 36 сверяет
оба режима на целом и на испорченном сохранении).  vbkx и плагины пула не
имеют - для них ничего не меняется; канал (pipe) - тоже по одной: его
нельзя перемотать дальше первой группы.

**Цифры** (тот же хост, нагрузка чужих задач 13..16):

| | X01-21 | X01-23 |
|---|---|---|
| python3 /LEVEL=1 | 3,3 с | 2,9 с |
| python3 /LEVEL=6 | 12,1 с | 4,7 с |
| python3 /LEVEL=9 | 11,2 с | 4,7 с |
| /usr/include /LEVEL=9 | 3,7 с | 2,3 с |
| python3 /LEVEL=9 /NOSOLID | 12,4 с | 6,5 с |

**Попутно.**  STS$K_WARN равен 0: конец потока при чтении вперёд хранится
отдельным флагом (`bend`), иначе пакет бесконечно перезаполнялся пустым -
поймано тестом 36 до того, как дошло до восстановления прерванных
сохранений.
